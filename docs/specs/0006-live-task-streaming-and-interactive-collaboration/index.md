# 0006. Live task streaming and interactive collaboration

**Date**: 2026-11-24
**Status**: Implemented

## Summary

This decision establishes live task streaming and interactive developer collaboration for autonomous runs. The FastAPI agent engine streams raw sandbox terminal chunks, thought decisions, and review verdicts to the Next.js web console using Server Sent Events (a standard browser protocol for unidirectional server push) backed by Redis Streams cursor replay. Developers can observe execution live in the virtualized terminal, provide steering guidance mid run, and answer clarification prompts when the agent pauses. This keeps developers in control of long running tasks without suffering connection drops, worker pool starvation, or serverless proxy timeouts.

## Requirements

**User stories**:
* As a software engineer watching an agent work, I want to see real time sandbox terminal logs, tool execution steps, and review scores in my browser console so that I understand exactly what the agent is doing at each step.
* As a developer whose task hits an ambiguous requirement, I want the agent to pause and ask for clarification so that I can provide steering guidance without restarting the entire task.
* As a team member reviewing an in progress run, I want to jump in midway or reconnect after a network hiccup and immediately catch up on all prior logs without missing context.

**Acceptance criteria**:
* **AC-1**: FastAPI Server Sent Events endpoint (`GET /api/v1/tasks/{task_id}/events`) streams structured event packets directly from Redis Streams using `XREAD BLOCK` with cursor replay via the `Last-Event-ID` header, pushing terminal chunks, agent thoughts, tool steps, and status transitions, sending `: ping\n\n` keep alive comments every 15 seconds.
* **AC-2**: Web console live inspector in `apps/web` connects directly to the FastAPI Server Sent Events stream using `@microsoft/fetch-event-source` with Clerk Bearer token authentication, feeding incoming terminal chunks into the virtualized `TerminalViewer` component with ANSI parsing and autoscroll pinning while synchronizing step progress badges and phase tabs.
* **AC-3**: Interactive collaboration interface enables developers to submit steering guidance (`POST /api/v1/tasks/{task_id}/intervene`), reply to clarification requests (`POST /api/v1/tasks/{task_id}/respond`), or abort the run (`POST /api/v1/tasks/{task_id}/abort`); endpoints authenticate with Clerk JWTs, enforce organization tenancy, persist records in `task_interventions`, and notify the agent engine via Redis.
* **AC-4**: LangGraph human in the loop interrupt state machine pauses sandbox execution, extends E2B sandbox timeouts, persists graph checkpoints, releases worker processes, and transitions task status to `awaiting_input` when the agent generates a clarification prompt; if unanswered within a 15 minute expiration deadline, a scheduled queue watchdog marks the task failed with an expiration audit event.
* **AC-5**: Resilient stream persistence buffers up to 10,000 events per task in a capped Redis Stream with a 24 hour time to live, serves in flight log polling for restricted networks, and upon task completion consolidates ANSI terminal logs and structured event transcripts into the `task_transcripts` table with gzip compression while recording immutable audit logs for all human interventions.

## Decision

**Chosen option**: Option 1: Unified Redis Streams cursor streaming architecture with FastAPI Server Sent Events downstream and authenticated REST intervention endpoints.

We adopt an architecture where FastAPI streams downstream execution events to browser clients over Server Sent Events directly from Redis Streams using `XREAD BLOCK` (eliminating dual Pub/Sub race conditions and supporting native replay via `Last-Event-ID`), while upstream developer guidance, clarification answers, and abort commands route through authenticated REST endpoints that push into task specific Redis queues.

**Implementation skills**: `fastapi-templates` (`wshobson/agents`, `.agents/skills/fastapi-templates/`) · `nextjs-app-router-patterns` (`wshobson/agents`, `.agents/skills/nextjs-app-router-patterns/`) · `tailwind-design-system` (`wshobson/agents`, `.agents/skills/tailwind-design-system/`) · `clerk-nextjs-patterns` (`clerk/skills`, `.agents/skills/clerk-nextjs-patterns/`)

## Feature design

### Data model sketch

Enhancements to existing PostgreSQL schema:

#### Table: `tasks` (column additions and status expansion)
* `status`: Expanded check constraint allowing `queued`, `in_progress`, `awaiting_input`, `completed`, `failed`, `cancelled` (reconciled with spec 0002 and spec 0004)
* `interruption_prompt`: TEXT (Nullable, clarification question or message generated by agent)
* `interruption_type`: VARCHAR(50) (Nullable, values: `clarification`, `confirmation`, `approval`)
* `interruption_options`: JSONB (Nullable, structured choices or input schema for response)
* `interruption_expires_at`: TIMESTAMPTZ (Nullable, deadline timestamp after which task aborts)

#### Table: `task_interventions` (new table)
* `id`: UUID (v7, Primary Key)
* `org_id`: UUID (Not Null, Foreign Key -> `organizations.id` ON DELETE CASCADE, Indexed)
* `task_id`: UUID (Not Null, Foreign Key -> `tasks.id` ON DELETE CASCADE, Indexed)
* `task_run_id`: UUID (Nullable, Foreign Key -> `task_runs.id` ON DELETE SET NULL, Indexed)
* `clerk_user_id`: VARCHAR(255) (Not Null, Clerk user ID string, matching `tasks.created_by_clerk_user_id`)
* `intervention_type`: VARCHAR(50) (Not Null, values: `guidance`, `clarification_response`, `abort`)
* `prompt_snapshot`: TEXT (Nullable, snapshot of the clarification question being answered)
* `payload`: JSONB (Not Null, message text, chosen option, or abort reason)
* `applied_at`: TIMESTAMPTZ (Nullable, timestamp when agent worker processed command)
* `created_at`: TIMESTAMPTZ (Not Null, Default `CURRENT_TIMESTAMP`)

#### Table: `task_transcripts` (new table)
* `id`: UUID (v7, Primary Key)
* `org_id`: UUID (Not Null, Foreign Key -> `organizations.id` ON DELETE CASCADE, Indexed)
* `task_id`: UUID (Not Null, Foreign Key -> `tasks.id` ON DELETE CASCADE, Indexed)
* `task_run_id`: UUID (Not Null, Foreign Key -> `task_runs.id` ON DELETE CASCADE, Indexed)
* `terminal_log`: BYTEA (Not Null, gzip compressed ANSI terminal logs)
* `events_json`: JSONB (Not Null, full chronological array of structured stream events)
* `total_lines`: INTEGER (Not Null, Default 0)
* `created_at`: TIMESTAMPTZ (Not Null, Default `CURRENT_TIMESTAMP`)

### State transitions

Task lifecycle states:
* `queued`: Task created from trigger, waiting for worker assignment.
* `in_progress`: Worker active, sandbox running, events streaming to Redis Streams.
* `awaiting_input`: Agent yielded clarification interrupt, sandbox frozen with extended timeout, worker thread released.
* `completed`: Work completed, review approved, pull request opened.
* `failed`: Execution failed, cycle limit reached, or interruption deadline expired.
* `cancelled`: Developer issued manual abort command.

Transition triggers:
* `in_progress` -> `awaiting_input`: Triggered by agent interrupt node when clarification is needed; E2B timeout extended to 15 minutes, LangGraph checkpoint saved, ARQ worker released, and delayed expiration job queued.
* `awaiting_input` -> `in_progress`: Triggered when developer submits response via `POST /api/v1/tasks/{id}/respond`; API updates task status, inserts intervention record, and enqueues resume worker job.
* `awaiting_input` -> `failed`: Triggered when 15 minute delayed ARQ watchdog job runs without an acknowledged answer.
* Any active state -> `cancelled`: Triggered when developer invokes `POST /api/v1/tasks/{id}/abort`.

### Event packet schemas (SSE protocol)

Events are delivered as standard Server Sent Events frames with specific event types and JSON data payloads:

* Terminal log chunk (`event: task.log`):
  `{"event_id": "1732450000000-0", "task_id": "UUID", "timestamp": "ISO-8601", "stream": "stdout", "chunk": "running pytest...\n"}`
* Agent step progress (`event: task.step`):
  `{"event_id": "1732450001000-0", "task_id": "UUID", "timestamp": "ISO-8601", "node": "forge", "step_number": 2, "status": "running", "details": {"action": "edit_file", "path": "src/main.py"}}`
* Human clarification interrupt (`event: task.interrupted`):
  `{"event_id": "1732450002000-0", "task_id": "UUID", "timestamp": "ISO-8601", "prompt": "Database migration requires dialect confirmation.", "options": ["PostgreSQL", "SQLite"], "expires_at": "ISO-8601"}`
* Interruption resumed (`event: task.resumed`):
  `{"event_id": "1732450003000-0", "task_id": "UUID", "timestamp": "ISO-8601", "intervention_id": "UUID"}`
* Task terminal status (`event: task.status`):
  `{"event_id": "1732450004000-0", "task_id": "UUID", "timestamp": "ISO-8601", "status": "completed", "failure_reason": null}`
* Connection keep alive:
  `: ping\n\n` (SSE comment frame sent every 15 seconds during silence)

### API surface

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| /api/v1/tasks/{task_id}/events | GET | task_id (UUID path), Last-Event-ID (header, optional) | text/event-stream chunks | Clerk Bearer token (JWT) | 401 unauthorized, 403 forbidden (org mismatch), 404 not found |
| /api/v1/tasks/{task_id}/intervene | POST | task_id (UUID path), message:string (req), action_type:string (req) | intervention_id, status: queued | Clerk Bearer token (JWT) | 400 invalid action, 403 forbidden, 404 not found, 409 task not running |
| /api/v1/tasks/{task_id}/respond | POST | task_id (UUID path), response:string (req), selected_option:string (opt) | intervention_id, status: accepted | Clerk Bearer token (JWT) | 400 missing answer, 403 forbidden, 404 not found, 409 not awaiting input |
| /api/v1/tasks/{task_id}/abort | POST | task_id (UUID path), reason:string (opt) | task_id, status: cancelled | Clerk Bearer token (JWT) | 403 forbidden, 404 not found, 409 task already terminal |
| /api/v1/tasks/{task_id}/transcript | GET | task_id (UUID path), run_id:UUID (opt) | terminal_log:string, events:array, total_lines:int | Clerk Bearer token (JWT) | 401 unauthorized, 403 forbidden, 404 not found |

### Value sourcing

| Action | Value produced / displayed | Source |
|---|---|---|
| Stream log chunk | event_id | Sourced from Redis Stream message ID (monotonic timestamp plus sequence) |
| Stream log chunk | chunk and stream type | Emitted by sandbox inner tool runner stdout and stderr pipes |
| Stream agent step | node, step_number, and details | Sourced from LangGraph node execution state callbacks |
| Stream interruption | interruption_prompt and options | Generated by agent clarification node before yielding graph interrupt |
| Stream interruption | interruption_expires_at | Computed by agent engine as CURRENT_TIMESTAMP plus interval '15 minutes' |
| Connect live stream | historical and live events | Read from Redis Stream `task:{task_id}:stream` starting from Last-Event-ID cursor using XREAD BLOCK |
| Submit intervention | clerk_user_id | Extracted from verified Clerk JWT claims |
| Submit intervention | org_id | Resolved by looking up repository owning the target task |
| Submit intervention | intervention_id | Generated as new UUIDv7 |
| Ingest response | prompt_snapshot | Copied from current `tasks.interruption_prompt` before clearing |
| Ingest response | applied_at | Captured by worker when resuming LangGraph checkpoint with Command |
| Replay historical transcript | terminal_log | Decompressed from `task_transcripts.terminal_log` BYTEA in PostgreSQL (or current Redis Stream if still in progress) |
| Replay historical transcript | events | Read from `task_transcripts.events_json` JSONB array in PostgreSQL (or current Redis Stream if still in progress) |

### Key invariants

* Server Sent Events connections stream directly from FastAPI to browser clients, bypassing Next.js serverless route handlers to avoid connection timeouts.
* Downstream streaming uses Redis Streams alone via `XREAD BLOCK`, eliminating race conditions between historical query and live push while supporting automatic replay from the `Last-Event-ID` header.
* Redis Streams storage for live task events is capped at 10,000 entries using MAXLEN with a 24 hour key expiration, preventing unbounded memory consumption.
* When an agent yields a clarification interrupt, the worker extends the E2B sandbox timeout to 15 minutes, saves the LangGraph checkpoint, releases the ARQ worker process, and schedules a persistent delayed queue watchdog.
* When a task enters awaiting input, an immutable 15 minute deadline is enforced; if no response is acknowledged, the delayed queue watchdog halts execution and marks the task failed.
* Developer responses use optimistic concurrency with conditional database updates; the first valid submission transitions status to in progress, and subsequent concurrent submissions receive 409 Conflict.
* If a client connects to the SSE endpoint for a task already in a terminal state, FastAPI transmits any remaining events from Redis Streams and closes the stream with a terminal status event.
* If a developer on a restricted network polls `GET /api/v1/tasks/{id}/transcript` while a task is in progress, the endpoint reads accumulated text from Redis Streams rather than failing with 404.
* Completed runs archive raw ANSI terminal logs with gzip compression into `task_transcripts`, providing permanent historical access after Redis keys expire.

### Security model

* Tenant organization scoping: All SSE stream requests and intervention endpoints enforce organization tenancy by verifying that the task repository belongs to the user organization.
* Authentication: Every client connection presents a verified Clerk JWT Bearer token; the SSE client automatically refreshes tokens before reconnecting.
* Role authorization: Any verified organization member may view streams, supply guidance, answer clarification prompts, or abort running tasks.
* Sanitization: Terminal log chunks are scrubbed of sensitive environment secrets and tokens before appending to Redis Streams.
* Immutability and audit: Every developer guidance comment, clarification reply, and abort command generates an immutable entry in `task_interventions` and `audit_logs`.

### Configuration required

* `NEXT_PUBLIC_AGENT_API_URL`: Base URL for the FastAPI agent engine (e.g. `http://localhost:8000` in local dev or production API domain), required in `apps/web/.env.local` for direct browser SSE connections
* `DATABASE_URL`: PostgreSQL connection string for tasks, interventions, and transcripts
* `REDIS_URL`: Redis connection string for Redis Streams
* `CLERK_SECRET_KEY`: Backend Clerk secret for verifying user authentication tokens

### Critical test scenarios

* Happy path live streaming: Task execution appends terminal stdout chunks and agent node steps to Redis Streams, FastAPI pushes events over SSE via XREAD BLOCK, and web console renders ANSI logs in TerminalViewer, verifies **AC-1**, **AC-2**
* Reconnection stream replay: Client disconnects, reconnects with Last-Event-ID header, receives missed events from Redis Streams, and seamlessly continues streaming, verifies **AC-1**, **AC-5**
* Human clarification interrupt and resume: Agent triggers clarification, task transitions to awaiting input, sandbox timeout is extended, worker process is released, web console displays prompt banner, user submits answer, and resuming worker restores checkpoint, verifies **AC-3**, **AC-4**
* Interruption deadline timeout: Task enters awaiting input, user does not respond within deadline window, delayed ARQ watchdog marks task failed with timeout reason, and sandbox resources terminate, verifies **AC-4**
* Concurrent response race condition: Two users submit answers to the same awaiting input prompt simultaneously; first request succeeds with 200 OK, second receives 409 Conflict, verifies **AC-3**
* In flight transcript polling fallback: Client queries `GET /api/v1/tasks/{id}/transcript` while task is in progress, endpoint reads accumulated logs from Redis Streams without waiting for task completion, verifies **AC-5**
* Organization tenant isolation: User belonging to Organization A attempts to connect to SSE stream or submit intervention for task in Organization B; request is rejected with 403 Forbidden, verifies **AC-1**, **AC-3**
* Historical transcript archival: Task finishes execution, archiver consolidates Redis events into gzip compressed PostgreSQL record, and subsequent GET /transcript requests return full logs, verifies **AC-5**

## Build plan

1. Database migration: Expand `tasks` status check constraint with `awaiting_input` and `completed`, add interruption metadata columns, and create `task_interventions` and `task_transcripts` tables with `org_id` and `clerk_user_id`, satisfies **AC-1**, **AC-4**
2. Redis Streams event appender: Implement worker event publisher appending capped Redis Streams (`MAXLEN ~ 10000`) for terminal chunks, agent thoughts, tool steps, and status events, satisfies **AC-1**, **AC-5**
3. FastAPI Server Sent Events endpoint: Create `GET /api/v1/tasks/{task_id}/events` using `sse-starlette` with `Last-Event-ID` cursor replay from Redis Streams via `XREAD BLOCK` and keep alive comments, satisfies **AC-1**
4. LangGraph human in the loop interrupt state machine: Build interruption node, E2B timeout extension, checkpoint persistence, worker process release, and delayed ARQ timeout watchdog in agent engine, satisfies **AC-4**
5. Authenticated REST intervention endpoints: Implement `POST /api/v1/tasks/{task_id}/intervene`, `/respond`, and `/abort` with Clerk auth, optimistic concurrency, and LangGraph resumption job dispatch, satisfies **AC-3**, **AC-4**
6. Web console SSE streaming client hook: Build `useTaskStream` custom React hook using `@microsoft/fetch-event-source` with automatic reconnection, Clerk token refresh, and state synchronization, satisfies **AC-1**, **AC-2**
7. Interactive task execution inspector UI: Implement split pane view in `apps/web/src/app/tasks/` combining virtualized `TerminalViewer`, step timeline tabs, clarification dialog banner, and steering input bar, satisfies **AC-2**, **AC-3**
8. Task completion transcript archiver and fallback reader: Build transcript service reading accumulated logs from Redis Streams during runs and archiving gzip compressed transcripts to PostgreSQL on completion, satisfies **AC-5**

## Consequences

**Positive**:
* Zero serverless timeout issues by connecting browser clients directly to FastAPI SSE endpoints.
* Eliminates transport race conditions and duplicates by using Redis Streams alone for both history and push.
* Releases worker processes during human input pauses, preventing worker pool starvation during the 15 minute wait.
* Explicit E2B timeout extension prevents sandboxes from prematurely shutting down while waiting for answers.
* Clean separation of concerns with unidirectional SSE downstream and authenticated REST actions upstream.

**Negative / tradeoffs**:
* Requires client configuration for direct API server URL (`NEXT_PUBLIC_AGENT_API_URL`) alongside Next.js app host.
* Sandboxes remain provisioned and consuming idle memory while waiting for human input during the 15 minute window.

**Neutral**:
* Developers connecting from restrictive corporate proxies that block HTTP streaming fall back to in flight polling via the transcript API.
