# 0009. Custom review rules and feedback learning

**Date**: 2026-11-28
**Status**: Accepted

## Summary

This specification lets engineering teams customize how agentsOnAir reviews code, teaches the reviewer from past feedback, and tracks review quality and turnaround in the web console. Organization admins configure default review rules, repository overrides, and curated example pull requests, while developers accept or dismiss review findings from either GitHub or the console. Dismissed findings build a lightweight team memory and gradually dampen or suppress noisy patterns, and a new Analytics page reports turnaround times, acceptance rates, and AI spend across repositories.

## Requirements

**User stories**:
- As an organization administrator, I want to define default review rules across the organization, override them per repository, and pin curated example pull requests so that reviews enforce our team conventions consistently.
- As a software engineer, I want to accept or dismiss review comments directly in GitHub or the web console so that repeated false positives fade away while valid preferences stick across future reviews.
- As an engineering lead, I want an Analytics dashboard showing review turnaround, autonomous task turnaround, finding acceptance rates, and daily AI costs so that I can measure quality and spending over time.

**Acceptance criteria**:
- **AC-1**: Organization admins (`org:admin`) can create, update, toggle, and soft delete (`deleted_at`) organization default review rules (`review_rules` where `repo_id IS NULL`) and repository specific rules (`review_rules` where `repo_id` is set), plus per repository overrides (`review_rule_overrides` setting `is_enabled` or `severity_override` on inherited org rules only), enforcing a limit of 25 active merged rules (`is_enabled = true` and `deleted_at IS NULL`) per repository under row locking (`SELECT ... FOR UPDATE`). Each rule stores `title`, `instruction`, `severity`, `category`, non empty `path_globs` (matched with a globstar aware matcher so `**/*` matches root files), and `is_enabled`; every rule or override change appends an immutable `audit_logs` record (`review_rule.created`, `review_rule.updated`, `review_rule.deleted`, `review_rule_override.updated`).
- **AC-2**: Organization admins (`org:admin`) can attach up to 5 curated example pull requests (`review_examples`) per repository (by `pr_number` or parsed same repository `pr_url`) with `classification` (`good` or `bad`) and a `guidance_note`. On creation or refresh, `GitHubGateway` verifies that the pull request belongs to the same repository (`base.repo.full_name == repo.full_name`, mapping missing or mismatched PRs to HTTP `422`), fetches metadata and diff via real GitHub HTTP endpoints, stores extracted `modified_files` (`JSONB` string list), redacts credential patterns (`[REDACTED]`), and caches a `cached_diff_summary` capped at 1,500 tokens preserving file headers. Every creation, refresh, or deletion appends an immutable `audit_logs` record (`review_example.created`, `review_example.refreshed`, `review_example.deleted`).
- **AC-3**: When `GitHubReviewPublisher.publish` submits a review with non empty inline comments and `fallback_applied` is false, it fetches review comments (`GET /repos/{owner}/{repo}/pulls/{pr_number}/reviews/{github_review_id}/comments`), matches `(path, line or original_line, body)` in order, and persists `pr_review_findings.github_comment_id` (logging a warning without failing the published review if comment lookup fails). Authenticated organization members can submit `accepted` or `dismissed` feedback with an optional `reason` and `remember_preference` flag via `POST /api/v1/reviews/findings/{finding_id}/feedback`. In parallel, `IngestGitHubWebhookUseCase` ingests `pull_request_review_thread` (`resolved` -> `accepted`, `unresolved` -> resets finding `feedback_state = 'none'` and `status = 'open'`) and `pull_request_review_comment` (`action == 'created'` replies matching `in_reply_to_id` to `github_comment_id` with case insensitive word boundary prefixes `dismiss`, `false positive`, `ignore`, `good catch`, `accept`) only from non bot actors whose `author_association` is `OWNER`, `MEMBER`, or `COLLABORATOR`, claiming `github_event_id` atomically via `INSERT ... ON CONFLICT DO NOTHING` before mutating finding or preference state.
- **AC-4**: Each `accepted` or `dismissed` feedback event updates `review_learned_preferences` keyed by `(repo_id, pattern_key)` under row locking, where `pattern_key` is `rule:{rule_id}` for rule linked findings or `{category}:{top_level_dir}` (`__root__` for root files) for general findings. Repeated identical feedback on the same `finding_id` is idempotent on `dismiss_count`, `accept_count`, and `consecutive_dismissals`. Dismissing with `remember_preference=true` or a non empty `reason` stores that instruction (otherwise storing a concise default instruction, and injecting into prompts only when `remember_preference=true`, `reason` is non empty, or `status == 'dampened'`). Two consecutive dismissals without an acceptance move the pattern to `dampened` (downgrading blocking severity to an `info` advisory note), and three consecutive dismissals move it to `suppressed` (filtered out of reported findings). An `accepted` feedback event resets `consecutive_dismissals = 0` and restores `active` status, and `org:admin` users can manually set `status` (`active`, `dampened` setting `consecutive_dismissals = 2`, or `suppressed`) or edit `instruction` in the console (`audit_logs` action `review_preference.updated`).
- **AC-5**: Using `tiktoken` (`cl100k_base` with `len // 4` fallback), `ContextBudgetAllocator` partitions Spec 0005's 32,000 token Tier 1 budget across `AGENTS.md` (up to 4,000 tokens), custom review context (up to 6,000 tokens: 2,000 path matched active rules prioritized by severity DESC then repo before org then `created_at` ASC, 2,000 matching `active`/`dampened` preferences, 2,000 file overlap ranked example PRs), and diff hunks (at least 22,000 tokens, expanding into unused `AGENTS.md` or custom context budget), pruning example PRs then preferences then lowest priority rules before diff hunks. Both `RunPRReviewUseCase` (Spec 0005) and `task_graph.py`'s `reviewer_node` (Spec 0004, passing merged rules, preferences, and examples in `task_context`) redact credentials and escape XML angle brackets (`<` and `>`) inside `<custom_rules>`, `<team_preferences>`, and `<example_prs>` delimiters, with system instructions barring user rules from overriding core security checks. `CodeReviewAnalyzerNode` and `ReviewerCriticAgent` validate optional `rule_id` outputs against injected active rules (dropping unknown or cross org IDs) and filter `suppressed` / downgrade `dampened` findings before `resolve_verdict()`, `min_severity`, and `max_comments`.
- **AC-6**: `GET /api/v1/analytics/overview` (accepting `days` in `7`, `30` default, or `90`, plus optional `repo_id` validated against the caller's org returning `404` if missing) computes organization scoped metrics directly from indexed PostgreSQL tables (`pull_request_reviews`, `pr_review_findings` joined via `pull_request_reviews`, `tasks`, `task_runs` joined via `tasks`, and `usage_events` joined via `tasks` / `pull_request_reviews`) with optional short lived Redis caching: PR review turnaround p50 and p95 in `ms`, autonomous task active turnaround p50 and p95 in `ms` (`GREATEST(0, EXTRACT(EPOCH FROM (completed_at - started_at)) - paused_seconds) * 1000`), finding counts by severity and category, acceptance rate (`0.0..1.0` or `null` when `accepted + dismissed == 0`), top triggered and dismissed non deleted rules, and zero filled UTC daily series for AI cost (`usage_events.estimated_cost_cents` split by `pr_review` vs `forge` plus `reviewer`) and daily p50 turnaround.
- **AC-7**: In `apps/web`, `apps/web/src/db/schema.ts` backfills Spec 0005 tables (`pullRequestReviews`, `prReviewFindings`, `repositories.reviewSettings`) alongside all new Spec 0009 tables and columns, and `GET /api/v1/reviews` lists organization scoped PR reviews (with optional `repo_id` filter and pagination). The sidebar adds **Analytics** (`/analytics`) using custom SVG and Tailwind CSS charts, KPI cards, `7d`/`30d`/`90d` and repository filters, rule tables, and zero state views, plus **Reviews** (`/reviews`) displaying PR reviews, findings, and Accept/Dismiss controls (with optional reason and Remember toggle) for all org members. `/settings` adds Organization Review Guidelines for `org:admin` users, and `/repositories` organizes its drawer into four tabs (`Guardrails`, `Rules & Overrides`, `Example PRs`, `Learned Preferences`), editable by `org:admin` and read only for members.

## Decision

**Chosen option**: Option 1: Relational review rules, deterministic glob and overlap selection inside Tier 1, dual channel feedback memory, and direct SQL analytics.

We store custom review rules (with soft deletes), per repository overrides, curated example pull requests (with stored `modified_files`), immutable feedback events, and learned preferences in PostgreSQL, match them deterministically into a bounded 6,000 token slice of Spec 0005's Tier 1 budget shared across PR reviews and the autonomous reviewer loop, and serve analytics directly from indexed source tables to lightweight SVG charts in Next.js.

**Implementation skills**: `fastapi-templates` (`wshobson/agents`, `.agents/skills/fastapi-templates/`) · `nextjs-app-router-patterns` (`wshobson/agents`, `.agents/skills/nextjs-app-router-patterns/`) · `clerk-nextjs-patterns` (`clerk/skills`, `.agents/skills/clerk-nextjs-patterns/`) · `tailwind-design-system` (`wshobson/agents`, `.agents/skills/tailwind-design-system/`)

## Feature design

**Data model sketch**:

- `review_rules` (new): `id` (UUIDv7 PK), `org_id` (UUID FK -> `organizations.id` CASCADE, not null), `repo_id` (UUID FK -> `repositories.id` CASCADE, nullable; `NULL` indicates an org default rule), `title` (`VARCHAR(200)`, not null), `instruction` (`TEXT`, not null), `severity` (`VARCHAR(20)`: `critical`, `major`, `minor`, `info`, not null), `category` (`VARCHAR(50)`: `security`, `bug`, `performance`, `architecture`, `style`, not null), `path_globs` (`JSONB` non empty list of strings, not null, default `["**/*"]`), `is_enabled` (`BOOLEAN`, not null, default `true`), `created_by` (`VARCHAR(255)`, not null), `deleted_at` (`TIMESTAMPTZ`, nullable), `created_at` (`TIMESTAMPTZ`), `updated_at` (`TIMESTAMPTZ`). Indexes: `(org_id, repo_id, is_enabled) WHERE deleted_at IS NULL`.
- `review_rule_overrides` (new): `id` (UUIDv7 PK), `org_id` (UUID FK -> `organizations.id` CASCADE, not null), `repo_id` (UUID FK -> `repositories.id` CASCADE, not null), `rule_id` (UUID FK -> `review_rules.id` CASCADE, not null), `is_enabled` (`BOOLEAN`, nullable), `severity_override` (`VARCHAR(20)`, nullable), `updated_by` (`VARCHAR(255)`, not null), `updated_at` (`TIMESTAMPTZ`). Unique index `uq_review_rule_overrides_repo_rule` on `(repo_id, rule_id)`.
- `review_examples` (new): `id` (UUIDv7 PK), `org_id` (UUID FK -> `organizations.id` CASCADE, not null), `repo_id` (UUID FK -> `repositories.id` CASCADE, not null), `pr_number` (`INTEGER`, not null), `pr_url` (`VARCHAR(512)`, not null), `pr_title` (`VARCHAR(512)`, not null), `classification` (`VARCHAR(20)`: `good`, `bad`, not null), `guidance_note` (`TEXT`, not null), `modified_files` (`JSONB` string list, not null, default `[]`), `cached_diff_summary` (`TEXT`, nullable), `cached_token_count` (`INTEGER`, not null, default `0`), `cached_at` (`TIMESTAMPTZ`, nullable), `created_by` (`VARCHAR(255)`, not null), `created_at` (`TIMESTAMPTZ`), `updated_at` (`TIMESTAMPTZ`). Unique index `uq_review_examples_repo_pr` on `(repo_id, pr_number)`.
- `pr_review_findings` (existing table extension): adds `rule_id` (UUID FK -> `review_rules.id` SET NULL, nullable) and `feedback_state` (`VARCHAR(20)`: `none`, `accepted`, `dismissed`, not null, default `none`). Indexes on `(rule_id, feedback_state)`, `(review_id, feedback_state)`, and `(github_comment_id) WHERE github_comment_id IS NOT NULL`.
- `review_finding_feedback` (new, append only): `id` (UUIDv7 PK), `org_id` (UUID FK -> `organizations.id` CASCADE, not null), `repo_id` (UUID FK -> `repositories.id` CASCADE, not null), `finding_id` (UUID FK -> `pr_review_findings.id` CASCADE, not null), `feedback_type` (`VARCHAR(20)`: `accepted`, `dismissed`, not null), `source` (`VARCHAR(32)`: `console`, `github_thread_resolved`, `github_comment_reply`, not null), `reason` (`TEXT`, nullable), `remember_preference` (`BOOLEAN`, not null, default `false`), `actor_id` (`VARCHAR(255)`, not null), `github_event_id` (`VARCHAR(128)`, nullable), `created_at` (`TIMESTAMPTZ`). Partial unique index `uq_review_finding_feedback_gh_event` on `(github_event_id) WHERE github_event_id IS NOT NULL`. Index on `(finding_id, created_at DESC)`.
- `review_learned_preferences` (new): `id` (UUIDv7 PK), `org_id` (UUID FK -> `organizations.id` CASCADE, not null), `repo_id` (UUID FK -> `repositories.id` CASCADE, not null), `rule_id` (UUID FK -> `review_rules.id` SET NULL, nullable), `source_feedback_id` (UUID FK -> `review_finding_feedback.id` SET NULL, nullable), `pattern_key` (`VARCHAR(255)`, not null), `instruction` (`TEXT`, not null), `dismiss_count` (`INTEGER`, not null, default `0`), `accept_count` (`INTEGER`, not null, default `0`), `consecutive_dismissals` (`INTEGER`, not null, default `0`), `status` (`VARCHAR(20)`: `active`, `dampened`, `suppressed`, not null, default `active`), `last_feedback_at` (`TIMESTAMPTZ`), `created_at` (`TIMESTAMPTZ`), `updated_at` (`TIMESTAMPTZ`). Unique index `uq_review_learned_prefs_repo_pattern` on `(repo_id, pattern_key)`.
- Analytics composite indexes (existing tables): `(org_id, status, created_at)` and `(repo_id, status, created_at)` on `pull_request_reviews`; `(org_id, status, completed_at)` on `task_runs`; `(pr_review_id, created_at)` on `usage_events`. Drizzle schema in `apps/web/src/db/schema.ts` backfills Spec 0005 (`repositories.reviewSettings`, `pullRequestReviews`, `prReviewFindings`) and mirrors all Spec 0009 tables and columns.

**State transitions**:

- `pr_review_findings.feedback_state`: `none` -> `accepted` or `dismissed` (toggles between `accepted` and `dismissed` on changing feedback, or resets `accepted`/`dismissed` -> `none` when a GitHub thread is marked `unresolved`; syncs `status` to `resolved` on `accepted`, `dismissed` on `dismissed`, or `open` on `none`).
- `review_learned_preferences.status`:
  - `active` -> `dampened` when `consecutive_dismissals == 2` (or admin sets `status = 'dampened'`, which sets `consecutive_dismissals = 2`)
  - `dampened` -> `suppressed` when `consecutive_dismissals >= 3`
  - `dampened` or `suppressed` -> `active` when an `accepted` feedback event arrives (resetting `consecutive_dismissals = 0`) or when an `org:admin` restores `active` in the console (also resetting `consecutive_dismissals = 0`)
  - `active` or `dampened` -> `suppressed` immediately when an `org:admin` manually suppresses it in the console

**Key invariants**:

- Every rule, override, example PR, feedback event, and learned preference is strictly scoped by `org_id` and verified against the caller's organization.
- Total active merged rules (`is_enabled = true` and `deleted_at IS NULL`) per repository never exceed 25, and curated example PRs per repository never exceed 5, enforced at write time under row locks (`SELECT ... FOR UPDATE` on `organizations` / `repositories`).
- `review_rule_overrides` may only target non deleted org default rules (`repo_id IS NULL`) within the same organization; clearing both `is_enabled` and `severity_override` to `null` deletes the override row.
- User authored rules, example notes, cached diffs, and feedback instructions pass through `[REDACTED]` secret scrubbing and XML angle bracket escaping inside `<custom_rules>`, `<team_preferences>`, and `<example_prs>`.
- Total prompt tokens across Tier 1 and Tier 2 remain strictly bounded to Spec 0005's 64,000 token limit; returned `rule_id`s are validated against injected active rules before insertion to prevent foreign key failures.
- Webhook feedback processing claims `github_event_id` atomically via `INSERT INTO review_finding_feedback ... ON CONFLICT DO NOTHING` before updating `pr_review_findings` or `review_learned_preferences` under `(repo_id, pattern_key)` row locking; repeated identical feedback on the same `finding_id` never increments counters twice.
- Suppressed patterns never emit findings in `CodeReviewAnalyzerNode` or `ReviewerCriticAgent`; dampened patterns downgrade to `info` severity before `resolve_verdict()`, `min_severity`, and `max_comments`.

**Security model**:

- `org:admin` Clerk role (`require_org_admin`) is required for all mutations to organization rules, repository rules, rule overrides, example pull requests, and learned preference status or instructions. Every admin mutation writes an immutable `audit_logs` record (`review_rule.*`, `review_rule_override.updated`, `review_example.*`, `review_preference.updated`).
- Any authenticated organization member (`resolve_caller_org`) can read rules, examples, learned preferences, PR reviews, and Analytics data for their organization, and can submit `accepted` or `dismissed` feedback on findings.
- GitHub webhooks (`pull_request_review_thread`, `pull_request_review_comment`) require HMAC SHA256 signature verification (`verify_github_signature`), non bot senders, and repository association (`OWNER`, `MEMBER`, or `COLLABORATOR`) so external fork commenters cannot poison team preferences.
- Example PR creation verifies `base.repo.full_name == repo.full_name` before caching, preventing cross tenant or arbitrary repository scraping.

**Critical test scenarios**:

- Happy path: `org:admin` creates an org default rule, overrides severity in a repo, attaches an example PR, and both PR review and Spec 0004 `reviewer_node` inject them inside XML tags; developer dismisses 3 distinct findings via console and authorized GitHub reply webhook, shifting `review_learned_preferences.status` from `active` to `dampened` to `suppressed`, and subsequent reviews omit that pattern, verifies **AC-1**, **AC-2**, **AC-3**, **AC-4**, **AC-5**.
- Root glob & idempotency checks: default `["**/*"]` matches root files (`README.md`); repeating `Dismiss` on the same `finding_id` or delivering a duplicate `X-GitHub-Delivery` webhook does not double increment `dismiss_count` or `consecutive_dismissals`; `unresolved` thread resets finding to `open`/`none`, verifies **AC-1**, **AC-3**, **AC-4**.
- Failure and boundary cases: enabling an org rule or adding a repo rule past 25 active rules, adding a 6th example PR, empty `path_globs`, or cross repo PR URL returns HTTP `422`; huge PR diffs prune examples then preferences before diff hunks so Tier 1 stays within 32k tokens; hallucinated `rule_id`s are stripped before DB insert, verifies **AC-1**, **AC-2**, **AC-5**.
- Auth and analytics: non admin calling rule/example/preference write endpoints receives HTTP `403`; external `NONE` association GitHub commenter webhook is ignored for feedback learning; `GET /analytics/overview?days=30&repo_id=...` returns accurate p50/p95 `ms` turnaround, acceptance rate, and split UTC daily costs (`404` on foreign `repo_id`), verifies **AC-1**, **AC-2**, **AC-3**, **AC-6**, **AC-7**.

## Consequences

**Positive**:
- Teams can enforce repository and organization conventions in plain language without maintaining custom static analysis plugins.
- Dual channel feedback capture meets developers in GitHub where they already resolve threads and reply to comments, reducing console friction.
- Deterministic path globbing and Tier 1 token sub budgeting add predictable prompt size and zero embedding infrastructure overhead.
- Soft deleting rules and isolating `review_finding_feedback` events preserve historical rule metrics and auditability.

**Negative / tradeoffs**:
- Backfilling `github_comment_id` requires one extra GitHub API read immediately after publishing an inline PR review.
- Direct SQL percentile aggregations on large organizations may eventually warrant enabling the short Redis cache or adding daily rollup tables if review volume grows tenfold.
- Restricting GitHub feedback webhooks to `OWNER`, `MEMBER`, and `COLLABORATOR` associations with explicit reply prefixes prevents prompt poisoning from external forks, at the cost of ignoring casual untagged discussion.

**Neutral**:
- Existing repositories without custom rules or example PRs continue to run Spec 0005 reviews unchanged, inheriting only `review_settings` defaults until an admin adds rules.
- `apps/web/src/db/schema.ts` must backfill Spec 0005 tables alongside Spec 0009 tables in task 1 of the build plan.
