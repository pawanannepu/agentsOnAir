## Summary
The change establishes the foundation for Spec 0005 (Full Repository Context Code Reviewer), introducing the database migration for PR reviews, structured findings, webhook routing with bot exclusion, two-tier context budget allocation, diff hunk parsing, and a GitHub review publisher with automatic 422 diff drift fallback. While the architectural framing and testing of pure logic are solid, the change cannot be merged in its current state because PR review jobs are never dispatched upon creation (leaving records permanently in `pending` and deadlocking subsequent reviews), `apps/web/src/db/schema.ts` was not updated with the new tables, the review node lacks actual LLM inference, and repository indexing analyzes the agent host filesystem rather than downloading the target repository tarball.

## Blockers

### 🔴 PR review execution is never scheduled (Pipeline Deadlock), `apps/agent/app/api/v1/endpoints/webhooks.py:56`
**Problem**: Ingestion of `pull_request` and `issue_comment` webhooks, as well as the manual review trigger endpoint `POST /repos/{repo_id}/pulls/{pr_number}/reviews`, creates a review record in `status="pending"`. However, neither endpoint dispatches a background task, enqueues an ARQ worker job, nor executes `RunPRReviewUseCase`. Because the review status remains `"pending"` indefinitely, the partial unique index `uq_pr_reviews_active_pr` permanently blocks all future review attempts for that PR with 409 Conflict.
**Why it matters**: In production, no PR review will ever run, and the PR gets permanently stuck in `pending`.
**Suggested fix**: Enqueue `RunPRReviewUseCase` in a background worker queue or FastAPI `BackgroundTasks` upon review creation, so reviews transition through `analyzing` -> `reviewing` -> `posting` -> `completed`/`failed`.

### 🔴 Web Drizzle schema is missing new tables and columns, `apps/web/src/db/schema.ts:50`
**Problem**: Alembic migration `e2a94519f802` adds `review_settings` to `repositories` and creates `pull_request_reviews` and `pr_review_findings` tables. However, `apps/web/src/db/schema.ts` was not updated with these schema definitions (only whitespace formatting changes were committed).
**Why it matters**: The web console's Drizzle ORM is out of sync with the database schema. Web queries cannot access PR reviews or repository review settings, breaking full-stack type safety and causing schema drift between web and agent apps.
**Suggested fix**: Define `pullRequestReviews`, `prReviewFindings`, and the `reviewSettings` JSONB column in `apps/web/src/db/schema.ts` matching the Alembic migration.

### 🔴 Missing LLM inference: `CodeReviewAnalyzerNode` contains no model call, `apps/agent/app/infrastructure/llm/reviewer_node.py:69`
**Problem**: `CodeReviewAnalyzerNode.analyze()` does not call Anthropic's API or invoke Claude Sonnet. When `simulated_findings` is None, it hardcodes an `if "TODO" in tier1_diff_context:` check and returns a hardcoded finding pointing to `src/main.py:1`.
**Why it matters**: Violates Spec 0005 AC-4 ("Review engine prompts Claude 3.5 Sonnet or Claude 3.7 Sonnet using a structured tool schema"). No real code review is performed on PR diffs.
**Suggested fix**: Integrate the Anthropic Claude API client using the structured tool schema defined in `StructuredFinding` with appropriate system instructions, prompts, and error handling.

### 🔴 Target repository tarball is never downloaded: `SymbolIndexer` indexes agent's local directory, `apps/agent/app/application/use_cases/run_pr_review.py:61`
**Problem**: `RunPRReviewUseCase.execute` calls `SymbolIndexer(repo_dir)` where `repo_dir` defaults to `"."`. It never downloads the shallow tarball for `head_commit_sha` via the GitHub API (`GET /repos/{owner}/{repo}/tarball/{head_commit_sha}`) into a temporary directory as required by AC-2.
**Why it matters**: In production, the review engine parses `apps/agent`'s own local source code instead of the user's PR repository files, returning incorrect symbols and failing to analyze external repositories.
**Suggested fix**: Fetch and extract the repository shallow tarball for `head_commit_sha` to a temporary directory (`tempfile.TemporaryDirectory`), pass that directory to `SymbolIndexer`, and ensure the temporary directory is cleaned up after execution.

## Major

### 🟠 Clean Architecture violation: Application use case directly imports infrastructure implementations, `apps/agent/app/application/use_cases/run_pr_review.py:13`
**Problem**: `RunPRReviewUseCase` imports `GitHubReviewPublisher` and `CodeReviewAnalyzerNode` directly from `app.infrastructure.*` and instantiates them as default arguments. `ingest_github_webhook.py` also imports `verify_github_signature` directly from `app.infrastructure.*`.
**Why it matters**: Violates the Clean Architecture rule in `AGENTS.md` ("Outer layers depend on inner layers, never the reverse... Use cases orchestrate domain logic and call infrastructure interfaces via dependency inversion"). Tightly couples application orchestration to concrete infrastructure implementations.
**Suggested fix**: Define abstract interfaces/Protocols in `app/application/ports/` (e.g., `ReviewPublisherPort`, `ReviewAnalyzerPort`), have use cases accept them via dependency injection, and instantiate concrete implementations in presentation layer factories/dependencies.

### 🟠 Missing multi-language / Tree-sitter symbol indexing and Redis caching (AC-2), `apps/agent/app/application/services/symbol_indexer.py:136`
**Problem**: `SymbolIndexer` uses Python's standard `ast` library and only inspects `*.py` files. It has zero support for TypeScript (`.ts`, `.tsx`), JavaScript, or other languages, despite Spec 0005 AC-2 explicitly mandating tree-sitter across Python and TypeScript. Additionally, no Redis caching of symbol graph snapshots keyed by commit SHA is implemented.
**Why it matters**: Pull requests modifying TypeScript code (such as `apps/web`) will have zero symbols extracted, defeating the purpose of a "full repository context" reviewer for the web frontend and non-Python repositories.
**Suggested fix**: Implement tree-sitter parsers for Python and TypeScript/TSX as specified in AC-2, and add Redis caching keyed by `f"symbols:{repo_id}:{head_commit_sha}"`.

### 🟠 Inaccurate token estimation (`len // 4`) risks context window overflow (AC-3), `apps/agent/app/application/services/context_budget_allocator.py:35`
**Problem**: Token counts are estimated using a naive `len(text) // 4` character count heuristic instead of `tiktoken` with `cl100k_base` encoding as mandated by Spec 0005 AC-3.
**Why it matters**: Code syntax (indentation, brackets, punctuation, short identifiers) typically compresses to ~2.5 - 3 characters per token with BPE. A diff estimated at 30k tokens could actually be 45k tokens, causing total context to exceed the strict 64k token limit and triggering LLM context length errors or unexpected truncation.
**Suggested fix**: Use `tiktoken.get_encoding("cl100k_base")` to accurately count tokens for diffs and symbols.

### 🟠 Database race condition in `create_review` causes unhandled 500 error instead of 409 Conflict, `apps/agent/app/infrastructure/db/repositories/pr_review_repository.py:97`
**Problem**: `SqlAlchemyPRReviewRepository.create_review` checks `find_active_by_repo_and_pr` before insertion, but does not wrap `await self._session.flush()` in a try/except for `sqlalchemy.exc.IntegrityError`. Concurrent requests that pass the initial check simultaneously will hit the partial unique constraint `uq_pr_reviews_active_pr` and raise an unhandled `IntegrityError`.
**Why it matters**: Under rapid webhook synchronize triggers, the second event crashes with an HTTP 500 error instead of returning a clean 409 Conflict or 200 ignored response.
**Suggested fix**: Catch `IntegrityError` during `self._session.flush()` and raise domain `ConflictError`.

### 🟠 `DiffHunkParser` fails on file paths with spaces and drops `start_line` for multi-line comments, `apps/agent/app/application/services/diff_hunk_parser.py:62`
**Problem**: `parts = line.split(" ")` breaks on file names containing spaces. Furthermore, `contains_new_line` only checks `hunk.new_start` (new file lines), making it incompatible with `side="LEFT"` (old file lines). In addition, `review_publisher.py` completely drops `start_line`, breaking multi-line comments on GitHub.
**Why it matters**: Inline comments on multi-line findings or renamed/spaced files will fail or be misrouted to summary.
**Suggested fix**: Use regex or git diff prefix parsing for paths (`--- a/...`, `+++ b/...`), support both `old_start` and `new_start` checks based on `side`, and include `start_line` in inline comment payloads.

### 🟠 Unqualified method call matching causes symbol graph pollution and O(N) performance cliff, `apps/agent/app/application/services/symbol_indexer.py:113`
**Problem**: `PythonSymbolVisitor` records any attribute call (e.g. `obj.get()`, `list.append()`) as a callee by bare name (`"get"`, `"append"`). When building Tier 2 context, `ContextBudgetAllocator` performs a linear scan over all repository symbols for each callee name and matches generic names like `get` to every class's `get` method.
**Why it matters**: Severe performance degradation on medium/large repositories (O(S * C) scans) and Tier 2 context pollution with unrelated methods.
**Suggested fix**: Maintain an inverted index for symbol lookup (`name_to_symbols: dict[str, list[str]]`) and filter out common standard library / built-in method names.

## Minor

### 🟡 Missing authentication on review API endpoints, `apps/agent/app/api/v1/endpoints/reviews.py:67`
**Problem**: The review endpoints accept `org_id` as an unvalidated parameter without verifying Clerk Bearer JWT tokens as required by the API specification.
**Why it matters**: Any client on the network can query reviews or trigger review runs without identity verification.
**Suggested fix**: Add Clerk JWT authentication dependency or header validation.

### 🟡 Missing filtering for `min_severity` and enforcement of `max_comments`, `apps/agent/app/infrastructure/github/review_publisher.py:74`
**Problem**: `Repository.review_settings` provides `min_severity` and `max_comments: 25`, but neither is enforced during review publication.
**Why it matters**: Repositories configured to only report major/critical issues or cap comments will receive all findings.
**Suggested fix**: Filter findings against `min_severity` and truncate inline comments to `max_comments` before publishing.

### 🟡 `update_finding_github_id` is never invoked after publishing review, `apps/agent/app/application/use_cases/run_pr_review.py:119`
**Problem**: Findings in the database retain `github_comment_id = None`, because comment IDs returned from the GitHub review submission are not persisted back to `pr_review_findings`.
**Why it matters**: Inline comments cannot be reconciled, updated, or tracked if GitHub users reply to or resolve them.
**Suggested fix**: Correlate published comment IDs from GitHub API response with finding records and persist them using `update_finding_github_id`.

### 🟡 Domain logic leakage: `resolve_verdict` implemented in infrastructure, `apps/agent/app/infrastructure/llm/reviewer_node.py:47`
**Problem**: The core business rule deterministically mapping finding severities to review verdicts (`changes_requested`, `comment`, `approved`) is implemented inside `CodeReviewAnalyzerNode` in the infrastructure layer.
**Why it matters**: Violates Clean Architecture domain layer responsibilities. The entity `PullRequestReview` is anemic.
**Suggested fix**: Move `resolve_verdict` to the `PullRequestReview` entity or a domain service.

### 🟡 Set non-determinism in Tier 2 symbol context allocation, `apps/agent/app/application/services/context_budget_allocator.py:124`
**Problem**: Iterating over `related_symbol_keys - target_symbol_keys` (a `set`) introduces non-deterministic symbol selection across runs due to Python's randomized hash seeding.
**Why it matters**: Successive reviews of the exact same commit could pack different symbols into the prompt.
**Suggested fix**: Sort symbol keys deterministically before packing them into Tier 2 context.

### 🟡 `list_pr_reviews` does not verify repository existence or tenant isolation, `apps/agent/app/api/v1/endpoints/reviews.py:127`
**Problem**: `list_pr_reviews` queries by `(org_id, repo_id, pr_number)` without checking if `repo_id` exists. If non-existent or belonging to another org, it returns 200 OK with `{"items": [], "total": 0}` instead of 404 Not Found.
**Why it matters**: Inconsistent error semantics compared to other repository-scoped endpoints.
**Suggested fix**: Validate repository existence and org ownership before executing the review query.

## Strengths
- **Clean database schema and concurrency protection**: The PostgreSQL tables `pull_request_reviews` and `pr_review_findings` with the partial unique index `uq_pr_reviews_active_pr` are well designed and accurately implement the spec's state machine and concurrency guard.
- **Resilient GitHub 422 line drift fallback**: The automatic fallback in `GitHubReviewPublisher` that captures 422 diff drift errors and reformats inline comments into the top-level review summary markdown prevents lost reviews when code drifts.
- **Thorough unit test coverage for pure logic components**: `test_pr_code_reviewer.py` has 12 passing tests cleanly validating webhook signatures, bot author exclusions, diff hunk containment, and verdict combinations.
