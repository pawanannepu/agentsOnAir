## Summary
This change implements Spec `0008` (guardrails, branch protection, risky-action approval gates, integer-cent LLM usage accounting, runtime/cost caps, sandbox network egress controls, and corresponding FastAPI + Next.js console surfaces) alongside Clerk v2 compact role normalization. The domain `PolicyEvaluator`, ceiling-cent `pricing.py`, database schema/migration, and atomic approval/usage SQL primitives are well structured and clean. However, two blockers will corrupt persisted `task_runs` token counters and break cross-worker approval/clarification resumes against real repositories, and several major defects affect command guardrail parsing, API pagination, DB connection resilience, approval state races, fail-open publish handling, placeholder-preview SSE auth, and integration test coverage.

## Blockers

### 🔴 Stale identity-map checkpoint reload clobbers `task_runs` token counters to zero, `apps/agent/app/application/use_cases/run_autonomous_loop.py:1174`
**Problem**: During `forge_node` and `reviewer_node`, `SqlAlchemyUsageRepository._write_usage` (`apps/agent/app/infrastructure/db/repositories/usage_repository.py:75-99`) increments `task_runs.prompt_tokens`, `completion_tokens`, `tokens_used`, and `estimated_cost_cents` either in a separate committed `iso_session` (`isolated=True`, used by `worker.py:259` and `test_guardrails.py:376`) or via a Core `update(TaskRunModel)` statement without `synchronize_session` (`isolated=False`). Later, `RunAutonomousLoopUseCase` calls `self._task_run_repo.update_checkpoint(...)` at `apps/agent/app/application/use_cases/run_autonomous_loop.py:1174` (and at `run_autonomous_loop.py:201` inside `_halt_with_failure` whenever `partial_diff` is non-empty). Because `SqlAlchemyTaskRunRepository.update_checkpoint` (`apps/agent/app/infrastructure/db/repositories/task_run_repository.py:151-173`) queries `TaskRunModel` without `populate_existing=True`, SQLAlchemy returns the stale cached instance from the outer session's identity map (`prompt_tokens=0`, `completion_tokens=0`, `tokens_used=0`), reassigning `current_run` to those stale zero (or pre-resume) values. `RunAutonomousLoopUseCase` then calls `self._task_run_repo.complete_run` (`run_autonomous_loop.py:230`, `1249`), which unconditionally overwrites `model.prompt_tokens`, `model.completion_tokens`, and `model.tokens_used = prompt_tokens + completion_tokens` in the database (`task_run_repository.py:196-198`).
**Why it matters**: Every completed task run, every review-cycle-exhausted run, and every budget/timeout-halted run with a `partial_diff` silently wipes `task_runs.prompt_tokens`, `completion_tokens`, and `tokens_used` back to `0` (or pre-resume counts) in PostgreSQL, breaking `GET /api/v1/tasks/{task_id}` (`budget_summary.tokens_used`) and billing reconciliation against `task_runs`.
**Suggested fix**: Add `.execution_options(populate_existing=True)` on `TaskRunModel` queries in `SqlAlchemyTaskRunRepository` (and `synchronize_session="fetch"` when `_write_usage` runs non-isolated), and remove the unconditional `prompt_tokens`/`completion_tokens`/`tokens_used` overwrite in `complete_run` (or read fresh database values before finalizing) when usage is tracked atomically per model call.

### 🔴 Cross-worker `resume()` skips repository cloning and ignores `git apply` failures, `apps/agent/app/application/use_cases/run_autonomous_loop.py:593`
**Problem**: When `RunAutonomousLoopUseCase.resume()` runs on a worker that does not hold the paused sandbox in its in-process `SandboxRegistry` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:570-606`), it allocates a fresh empty sandbox, calls `workspace.init_workspace(repo_url_with_read_token=None, ...)` without cloning the repository or checking out `base_branch`, and then runs `git apply --whitespace=nowarn .aoa_partial.patch && rm -f .aoa_partial.patch` without checking the command's `exit_code`. It also never updates `sandbox_runs.sandbox_id` with the newly provisioned `sandbox.id`.
**Why it matters**: For any real repository task that modifies existing tracked files or needs repository context after resuming from an approval or clarification pause on another worker, the empty workspace lacks the codebase and `base_branch` history, causing `git apply` to fail silently, dropping the partial work, leaving `.aoa_partial.patch` untracked in the workspace (where `collect_workspace_diff` will pick it up), and leaving `sandbox_runs` pointing to a dead sandbox ID for any subsequent abort/timeout cleanup.
**Suggested fix**: Re-obtain a short-lived `contents:read` installation token (or clone URL from repository metadata when the repo was cloned on `execute`) and pass it to `init_workspace` during cross-worker `resume()`, check the `git apply` exit code (raising an explicit failure if rehydration fails) and clean up `.aoa_partial.patch` in a `finally`/always-run shell command, and update `sandbox_runs` with the replacement `sandbox.id`.

## Major

### 🟠 `PolicyEvaluator.classify_command` misses unspaced shell operators, command wrappers, and `git` global flags, `apps/agent/app/domain/services/policy_evaluator.py:264`
**Problem**: `classify_command` tokenizes commands with `shlex.split(stripped_cmd)` (where `punctuation_chars` defaults to `False`), splits segments only on exact tokens `{"&&", "||", ";", "|"}`, inspects only `segment[0]` as the executable (`policy_evaluator.py:274`), and checks `git` subcommands via `args_lower[0]` (`policy_evaluator.py:309`). Commands written without spaces around operators (`echo secret>.env`, `echo ok&&rm -rf /`, `true;curl https://evil.com`), invocations through shell wrappers or env prefixes (`sh -c "rm -rf /"`, `bash -c "curl ..."`, `env rm -rf /`, `VAR=1 curl ...`), and `git` with leading flags (`git -C . push --force`, `git -c x=y reset --hard`) all evaluate as `decision="allow"`.
**Why it matters**: Untrusted agent shell commands can bypass `external_network` (`off_after_install` block), `destructive_shell`, `force_git_op`, and `sensitive_path_edit` approval gates using standard valid `sh` syntax.
**Suggested fix**: Tokenize with `shlex.shlex(stripped_cmd, posix=True, punctuation_chars=True)` (plus handling `1>`/`2>`/`&>` descriptors), strip leading `KEY=VALUE` assignments and wrapper executables (`env`, `command`, `nohup`, `sudo`, and recursive parsing for `sh`/`bash -c` scripts), and resolve the `git` subcommand by skipping known global flags (`-C`, `-c`, `--git-dir`, etc.) before classifying.

### 🟠 `GET /api/v1/repositories` pagination ignores `offset` when `offset < limit` or not a multiple of `limit`, `apps/agent/app/api/v1/endpoints/repositories.py:79`
**Problem**: `list_repositories` exposes `limit` and `offset` query parameters (`repositories.py:73-74`), but translates them to `page = (offset // limit) + 1` before calling `repo_repo.list_by_org(org.id, page=page, page_size=limit)` (`repositories.py:79-80`). Any request with `offset=10, limit=50` resolves to `page=1` (`OFFSET 0`), and `offset=25, limit=20` resolves to `page=2` (`OFFSET 20`).
**Why it matters**: Callers paging through connected repositories via `offset` receive duplicate first-page or misaligned results.
**Suggested fix**: Pass `offset` and `limit` directly to a repository method (or add `offset` parameter support to `list_by_org`) instead of integer-dividing `offset // limit`.

### 🟠 Async SQLAlchemy engine lacks `pool_pre_ping` and `pool_recycle`, causing `asyncpg.InterfaceError` 500s, `apps/agent/app/infrastructure/db/session.py:9`
**Problem**: `create_async_engine` in `apps/agent/app/infrastructure/db/session.py:9-13` is instantiated with no `pool_pre_ping=True` or `pool_recycle` settings, even though `config.py:40-49` configures SSL for managed serverless PostgreSQL (which drops idle TCP connections). When the pool returns a stale closed connection on a subsequent API request (such as the transient `500` observed during `/check verify` on `PATCH /api/v1/repositories/{repo_id}/guardrails`), `asyncpg` raises `InterfaceError: connection is closed`.
**Why it matters**: Idle pooled connections produce intermittent unhandled `500 Internal Server Error` responses across API endpoints after short periods of inactivity.
**Suggested fix**: Configure `pool_pre_ping=True` and `pool_recycle=300` on `create_async_engine` in `apps/agent/app/infrastructure/db/session.py`.

### 🟠 Approval decision endpoint accepts already-expired approvals and races with `/abort`, `apps/agent/app/api/v1/endpoints/tasks.py:559`
**Problem**: `SqlAlchemyTaskApprovalRepository.decide_atomic` (`apps/agent/app/infrastructure/db/repositories/task_approval_repository.py:161-166`) only checks `TaskApprovalModel.status == "pending"` and never checks `TaskApprovalModel.expires_at > now`, so `POST /api/v1/tasks/{task_id}/approvals/{approval_id}/decision` allows approving an approval whose deadline has already passed whenever the ARQ watchdog has not yet run. In addition, when `decision == "rejected"`, `tasks.py:637` calls `task_repo.clear_interruption(..., new_status="failed")` without verifying `task.status == "awaiting_input"` (unlike `claim_interruption` on `approved`), while `abort_task` (`tasks.py:705-764`) cancels the task without bumping `task_runs.version` or closing any pending `task_approvals` row. A concurrent `rejected` decision can overwrite a `cancelled` task back to `failed`, and aborting leaves a `pending` row in `task_approvals`.
**Why it matters**: Violates AC-4's `409 already decided or expired` guarantee, enables race conditions between `/abort` and `/approvals/{id}/decision`, and leaves dangling `pending` rows blocked by `uq_task_approvals_pending_task` if the task is ever re-triggered.
**Suggested fix**: Enforce `TaskApprovalModel.expires_at > now` inside `decide_atomic` (returning `409` if expired), make `abort_task` atomically mark any `pending` `task_approvals` row as `rejected`/`expired` and advance `task_runs.version`/`status` to `cancelled`, and guard the `rejected` path in `decide_task_approval` with `claim_interruption(..., new_status="failed")`.

### 🟠 `host_publish_node` fails open on non-approved resume, and `ApprovalRequiredError` crashes the worker in `forge_node`, `apps/agent/app/infrastructure/llm/task_graph.py:343`
**Problem**: In `host_publish_node` (`apps/agent/app/infrastructure/llm/task_graph.py:342-350`), if `already_approved` is `False` and `_interrupt_for_classification` returns a `resume_value` whose `decision` is not `"approved"`, the function neither raises nor returns early—it falls straight through to `github_gateway.push_branch` and `create_pull_request`. Meanwhile, in `forge_node` (`task_graph.py:254-267`), a non-approved `resume_value` re-raises `ApprovalRequiredError`, which is not caught by `RunAutonomousLoopUseCase._run_cycles` (`run_autonomous_loop.py:907-949`).
**Why it matters**: Any unexpected resume payload (or direct `use_case.resume()` invocation without an `"approved"` decision) would either push code and open a PR without approval in `host_publish_node` or crash the ARQ worker with an unhandled exception in `forge_node`.
**Suggested fix**: Fail closed in both `host_publish_node` and `forge_node` by raising an explicit domain failure (e.g., `GuardrailBlockedError` or `ApprovalRejectedError`) when a resumed approval interrupt lacks `"approved"`, and catch it in `_run_cycles` via `_halt_with_failure`.

### 🟠 `DockerSandboxSession` and `E2BSandboxSession` omit `meta_dir`, creating a cross-task `/tmp/aoa-hooks/pre-push` race, `apps/agent/app/infrastructure/sandbox/docker_sandbox.py:34`
**Problem**: `DockerSandboxSession` creates a per-session `self._meta_dir` and passes `GIT_CONFIG_SYSTEM=self._system_gitconfig` (`docker_sandbox.py:34,86`), and `E2BSandboxSession` wraps a delegate `MockSandboxSession` (`e2b_sandbox.py:21-30`), yet neither class exposes a `meta_dir` property (unlike `MockSandboxSession` at `mock_sandbox.py:67-69`). ### 🟠 Sandbox network egress enforcement in `DockerSandboxSession` and `E2BSandboxProvider` is stubbed out / dead code, `apps/agent/app/infrastructure/sandbox/docker_sandbox.py:161`
**Problem**: `DockerSandboxProvider.create_sandbox` (`docker_sandbox.py:197-220`) never launches a Docker container or passes `container_name` to `DockerSandboxSession`, so `if self._container_name` in `DockerSandboxSession.restrict_network` (`docker_sandbox.py:173-185`) is never entered; moreover, `restrict_network` has no enforcement path when `mode == "allowlist"` and `domains` is non-empty. **Why it matters**: Under AC-7, setting `network_egress_mode` to `off_after_install` or `allowlist` only flips in-memory boolean attributes (`_network_restricted`) in production unless real container/E2B clients are wired, leaving outbound network access unrestricted at the OS/sandbox layer if non-CLI tools (`python`, `urllib`, `node`) are executed.
**Suggested fix**: Wire real `e2b` SDK sandbox creation when `self._api_key` is set, spawn/manage real network-isolated Docker containers when `container_name` is used (including DNS/firewall allowlist rules for non-empty `allowlist` mode), or explicitly fail closed / reject `docker` `allowlist` mode with non-empty domains if host firewalling is unsupported.

## Minor

### 🟡 `init_workspace` ignores `install_command` failures and runs unbounded by `timeout_minutes`, `apps/agent/app/application/services/sandbox_workspace.py:223`
**Problem**: `SandboxWorkspace.init_workspace` runs `install_command` (`sandbox_workspace.py:223-232`) without checking `install_res.exit_code != 0`, and `RunAutonomousLoopUseCase.execute` (`run_autonomous_loop.py:385-391`) does not wrap `init_workspace` in `asyncio.wait_for(..., timeout=remaining)`.

### 🟡 `SandboxWorkspace.run_test` skips verifying `command`, and `is_protected_branch` ignores `protected_branch_guard`, `apps/agent/app/application/services/sandbox_workspace.py:311`
**Problem**: `SandboxWorkspace.run_test` (`sandbox_workspace.py:311-339`) bypasses `PolicyEvaluator.classify_command` regardless of the command string passed, and `PolicyEvaluator.is_protected_branch` (`policy_evaluator.py:205-215`) ignores `policy.protected_branch_guard`.
**Why it matters**: If a future ReAct agent invokes `run_test` with an LLM-supplied command instead of the configured `repo.config["test_command"]`, command guardrails would be bypassed; similarly, constructing `EffectiveGuardrailPolicy(protected_branch_guard=False)` directly in Python would still block branches.

### 🟡 `RunPRReviewUseCase` ignores postflight `halt_reason` from `UsageTracker`, `apps/agent/app/application/use_cases/run_pr_review.py:131`

### 🟡 Longest-prefix collision and `bool` acceptance in `pricing.py`, `apps/agent/app/core/pricing.py:102`
**Problem**: `get_model_rate` iterates `DEFAULT_MODEL_RATES` and overrides in insertion order (`pricing.py:102-111`), where `"gpt-4o"` precedes `"gpt-4o-mini"`, so versioned names like `"gpt-4o-mini-2024-07-18"` match `"gpt-4o"` (16x rate overestimate). Also, `_load_overrides` (`pricing.py:87`) accepts `bool` values (`isinstance(True, int) is True`) and re-parses `MODEL_PRICING_OVERRIDES_JSON` on every invocation.

**Suggested fix**: Sort override and default keys by descending length before prefix matching, reject `isinstance(..., bool)` in `_load_overrides`, and cache parsed overrides.
