## Summary
The change establishes the foundational polyglot monorepo for agentsOnAir, wiring Turborepo with Next.js 16 in `apps/web` and Python FastAPI with `uv` in `apps/agent`. The repository structure, Docker Compose services, and test harnesses are neatly set up with impressive execution speed. However, merge is blocked by an ambient `LayoutProps` type in `RootLayout` that breaks `tsc --noEmit` on clean checkouts, a Pydantic Settings crash when CORS origins are configured via standard environment variables, omission of the specified MinIO service in Docker Compose, and dummy stub commands for Python linting and typechecking.

## Blockers
### 🔴 Unresolved `LayoutProps` global type breaks typecheck on clean checkout, `apps/web/src/app/layout.tsx:20`
**Problem**: `RootLayout({ children }: LayoutProps<"/">)` relies on ambient type `LayoutProps`, which is only generated into `.next/types/routes.d.ts` after running `next dev` or `next build`. On a clean checkout or in CI where `.next` does not exist, running `pnpm typecheck` (`tsc --noEmit`) fails with `TS2304: Cannot find name 'LayoutProps'`.
**Why it matters**: CI pipelines and fresh checkouts that execute `typecheck` before `build` will fail to compile.
**Suggested fix**: Type `RootLayout` with standard React props (`{ children: React.ReactNode }` importing `ReactNode` from `"react"`) so TypeScript compilation is completely self-contained and independent of ephemeral build caches.

## Major
### 🟠 `ALLOWED_ORIGINS` crashes server startup on comma-separated environment variables, `apps/agent/app/core/config.py:14`
**Problem**: `Settings` uses Pydantic Settings with `ALLOWED_ORIGINS: list[str] = [...]`. In Pydantic v2, passing a comma-delimited string via environment variable or `.env` (e.g. `ALLOWED_ORIGINS=http://localhost:3000,https://app.agentsonair.com`) raises a fatal `SettingsError` during settings initialization.
**Why it matters**: Production and staging deployments that inject environment variables in standard comma-separated format will crash the FastAPI process on launch.
**Suggested fix**: Add a `@field_validator("ALLOWED_ORIGINS", mode="before")` to `Settings` that splits comma-separated strings into a list of trimmed strings.

### 🟠 Missing MinIO service in `docker-compose.yml` contradicts spec 0001, `docker-compose.yml:1`
**Problem**: Spec 0001 explicitly commits: *"Local development will use Docker Compose for local PostgreSQL, Redis, and MinIO storage services"*, and marks the follow-up checklist item `Create Docker Compose configuration for local PostgreSQL, Redis, and MinIO development services` as complete `[x]`. However, `docker-compose.yml` only includes `postgres` and `redis`, omitting `minio` entirely.
**Why it matters**: S3-compatible object storage is specified for run logs, execution traces, and diff artifacts; missing MinIO breaks offline development parity and local service orchestration.
**Suggested fix**: Add the `minio` container definition and volume to `docker-compose.yml`, and add corresponding S3 endpoint/credential variables to `.env.example`.

### 🟠 Python lint and typecheck scripts are no-op echo stubs, `apps/agent/package.json:8`
**Problem**: In `apps/agent/package.json`, `"lint"` and `"typecheck"` are implemented as `echo "Agent lint ready"` and `echo "Agent typecheck ready"`. Spec 0001 (line 59) explicitly specified: *"Turborepo can pipeline linting, type checking with pyright, and pytest runs alongside Next.js tasks"*. Neither `pyright` (or `mypy`) nor a linter (`ruff`) is installed in `apps/agent/pyproject.toml`.
**Why it matters**: Running `pnpm lint` and `pnpm typecheck` across the monorepo produces false positive passes, leaving the entire Python agent service completely unverified by static analysis.
**Suggested fix**: Add `pyright` and `ruff` to `[dependency-groups] dev` in `pyproject.toml`, and update `apps/agent/package.json` scripts to run `uv run ruff check .` and `uv run pyright .`.

## Minor
### 🟡 Experimental Python 3.14 pinned in `.python-version`, `apps/agent/.python-version:1`
**Problem**: `apps/agent/.python-version` pins `3.14`, while spec 0001 specifies Python 3.12 (`FastAPI (Python 3.12)`).
**Why it matters**: Python 3.14 is currently unreleased/alpha. Pinned 3.14 forces `uv` to look for or download an experimental runtime, risking environment inconsistencies and package incompatibilities across developer machines.
**Suggested fix**: Change `.python-version` to `3.12` to align with spec 0001 and stable LTS releases.

### 🟡 Duplicate untracked lockfile `apps/web/pnpm-lock.yaml`, `apps/web/pnpm-lock.yaml:1`
**Problem**: `apps/web/pnpm-lock.yaml` was left behind after running `create-next-app` inside the subpackage, alongside the root workspace `pnpm-lock.yaml`.
**Why it matters**: In a pnpm workspace, subpackage lockfiles are ignored by pnpm and lead to confusion, stale dependency tracking, and potential merge conflicts.
**Suggested fix**: Remove `apps/web/pnpm-lock.yaml` so only the root workspace lockfile is tracked.

### 🟡 Missing Pydantic response models and inconsistent health endpoints, `apps/agent/app/api/v1/endpoints/health.py:7`
**Problem**: Neither `/health` in `main.py` nor `/api/v1/health` defines a Pydantic `response_model`. In addition, their return payloads differ in structure and naming: `/health` returns `{"status": "ok", "service": "agent-engine"}` while `/api/v1/health` returns `{"status": "healthy", "service": "agent-engine", "version": "0.1.0"}`.
**Why it matters**: Omitting `response_model` prevents OpenAPI from documenting typed response schemas for automated client generation. Inconsistent status values complicate health checking and synthetic monitoring.
**Suggested fix**: Define a shared `HealthResponse(BaseModel)` with consistent status values (`"healthy"`) and declare it on both endpoints.
