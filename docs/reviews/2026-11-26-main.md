## Summary
This uncommitted working tree implements Spec 0006 (live task streaming over Server Sent Events backed by Redis Streams, LangGraph human in the loop pause and resume, developer steering and abort endpoints, transcript archival, and the console task detail UI) alongside Spec 0007 (Clerk authentication, route protection, organization onboarding and switching, Svix webhooks, and isolated lazy organization sync). The core Redis Streams replay model, optimistic locking on clarification responses, atomic PostgreSQL organization upserts, and Next.js Suspense guards are well conceived, and unit/integration tests cover many key paths. However, three production blockers remain: the SSE endpoint pins a database session and transaction for the entire stream lifetime, an operator abort during an active execution cycle can be overwritten by a PR and a `completed` status, and raw command output containing environment secrets is streamed unredacted to Redis Streams and transcript archives.

## Blockers
### 🔴 SSE endpoint pins a database session for the entire stream lifetime, `apps/agent/app/api/v1/endpoints/tasks.py:239`
**Problem**: `stream_task_events` injects `db: AsyncSession = Depends(get_db)` (`apps/agent/app/api/v1/endpoints/tasks.py:239`), runs `authorize_task_org` (`apps/agent/app/api/v1/endpoints/tasks.py:248`), and returns `EventSourceResponse(event_generator(), ping=15)` (`apps/agent/app/api/v1/endpoints/tasks.py:306`). FastAPI does not exit `get_db()` (`apps/agent/app/infrastructure/db/session.py:24`) until the streaming response closes.
**Why it matters**: Every open SSE browser tab keeps a PostgreSQL connection checked out of the SQLAlchemy pool in an `IDLE in transaction` state for the entire duration of the task or 15 minute pause, exhausting the connection pool under modest concurrent usage and blocking all other API requests.
**Suggested fix**: Authorize and load the initial task state inside a short lived committed or rolled back session (`async_session_factory()` or explicit session closure) before creating `EventSourceResponse`, so zero database connections or transactions remain held while streaming events.

### 🔴 Mid cycle abort race still opens a PR and overwrites cancelled status, `apps/agent/app/application/use_cases/run_autonomous_loop.py:343`
**Problem**: `RunAutonomousLoopUseCase._run_cycles` only checks `cur_task.status == "cancelled"` at the top of the `while` loop (`apps/agent/app/application/use_cases/run_autonomous_loop.py:343-345`) before `graph.ainvoke(...)`. After `graph.ainvoke(...)` returns, it proceeds without rechecking task status to record an interruption (`apps/agent/app/application/use_cases/run_autonomous_loop.py:517`), fail on cycle exhaustion (`apps/agent/app/application/use_cases/run_autonomous_loop.py:614`), or push code to GitHub, open a pull request, and call `update_status(..., status="completed")` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:645-694`). Similarly, `resume()` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:229-266`) allocates a sandbox and marks `task_run` as `"running"` before checking whether the task was cancelled.
**Why it matters**: Calling `POST /api/v1/tasks/{task_id}/abort` while a Forge or Reviewer cycle is running fails to stop publication: the engine still pushes changes, opens a pull request, and overwrites the operator's `cancelled` status back to `completed` or `failed`.
**Suggested fix**: Check `task.status == "cancelled"` at the entry of `resume()` before allocating sandboxes or mutating `task_runs`, recheck task status right after `graph.ainvoke(...)` (both before pausing and before pushing or opening a PR), and use a conditional update or row lock when transitioning `tasks` out of active states so a cancelled task can never transition to `completed`, `failed`, or `awaiting_input`.

### 🔴 Terminal chunks stream unredacted secrets to Redis Streams and archives, `apps/agent/app/application/services/sandbox_workspace.py:50`
**Problem**: `SandboxWorkspace` appends raw shell commands (`init_workspace`, `run_baseline_tests`, `run_test`, `run_command` at `apps/agent/app/application/services/sandbox_workspace.py:50-65, 93-105, 148-157, 178-187`) and raw `result.stdout` / `result.stderr` directly to Redis Streams via `append_event("task.log", ...)` and `stream_event(...)`, which are later archived to PostgreSQL `task_transcripts`. Both `MockSandboxSession` (`apps/agent/app/infrastructure/sandbox/mock_sandbox.py:50`) and `DockerSandboxSession` (`apps/agent/app/infrastructure/sandbox/docker_sandbox.py:51`) also pass `os.environ.copy()` into subprocess execution.
**Why it matters**: Spec 0006 requires sanitizing terminal log chunks of sensitive environment secrets and tokens before appending to Redis Streams. Any repository read token in `repo_url_with_read_token`, API key, or server environment secret printed to stdout or stderr is exposed over SSE to all organization viewers and stored permanently in `task_transcripts`.
**Suggested fix**: Strip host secret environment variables from local/Docker subprocess environments, redact credentials from logged git URLs, and apply a centralized secret scrubbing filter inside `SandboxWorkspace` (and/or `InMemoryOrRedisEventStreamer.append_event`) before writing `task.log` and `task.step` payloads to Redis Streams.

## Major
### 🟠 Clean Architecture dependency inversion violation in use case, `apps/agent/app/application/use_cases/run_autonomous_loop.py:38`
**Problem**: `RunAutonomousLoopUseCase` directly imports concrete infrastructure modules `app.infrastructure.llm.task_graph` (`Command`, `PostgresTaskCheckpointSaver`, `TaskGraphState`, `build_task_cycle_graph`) and `app.infrastructure.sandbox.registry` (`SandboxRegistry`) at `apps/agent/app/application/use_cases/run_autonomous_loop.py:38-44`, and instantiates `PostgresTaskCheckpointSaver()` and `build_task_cycle_graph(...)` inside `_run_cycles` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:334-340`).
**Why it matters**: This directly violates root `AGENTS.md` architecture rules ("Outer layers depend on inner layers, never the reverse" and "Use cases orchestrate domain logic and call infrastructure interfaces via dependency inversion"), coupling the application layer to LangGraph and an in memory registry implementation.
**Suggested fix**: Define protocol ports in `apps/agent/app/application/ports/` for graph cycle execution/resumption and paused sandbox tracking, inject implementations into `RunAutonomousLoopUseCase.__init__`, and move LangGraph imports out of `app/application/`.

### 🟠 Developer steering guidance dropped on resume, `apps/agent/app/application/use_cases/run_autonomous_loop.py:347`
**Problem**: At the top of `_run_cycles`, `_collect_guidance_messages` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:292-306, 347`) reads all unapplied `"guidance"` interventions and marks `applied_at` on each row in PostgreSQL. When `is_resuming_cycle` is true (`apps/agent/app/application/use_cases/run_autonomous_loop.py:381-386`), the graph resumes via `graph.ainvoke(Command(resume=resume_response), config=config)`, which restores the pre pause checkpoint state and never merges the newly collected `guidance_messages`.
**Why it matters**: Any steering guidance submitted by a developer while a task is `awaiting_input` is marked `applied_at` in the database and silently lost without reaching `ForgeCoderAgent`.
**Suggested fix**: Pass newly collected `guidance_messages` into the resumed LangGraph state (for example via `Command(resume=..., update={"guidance_messages": ...})` or `aupdate_state` before resuming), or defer marking guidance applied until `forge_node` consumes it.

### 🟠 `/intervene` accepts `action_type="abort"` without aborting the task, `apps/agent/app/api/v1/endpoints/tasks.py:100`
**Problem**: `InterveneRequest` permits `action_type` matching `"^(guidance|abort)$"` (`apps/agent/app/api/v1/endpoints/tasks.py:100`). `intervene_task` (`apps/agent/app/api/v1/endpoints/tasks.py:328-359`) persists a `TaskIntervention` with `intervention_type="abort"`, logs an audit event, and returns `{"status": "queued"}`, while neither `intervene_task` nor `_collect_guidance_messages` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:301`) ever cancels the task.
**Why it matters**: Clients using the documented `abort` option on `/intervene` receive `200 OK` believing the task is queued for cancellation while execution continues uninterrupted.
**Suggested fix**: Either reject `"abort"` on `InterveneRequest` (directing callers to `POST /tasks/{task_id}/abort`) or delegate `action_type == "abort"` in `intervene_task` to the same cancellation and sandbox cleanup path used by `abort_task`.

### 🟠 Process local `SandboxRegistry` and omitted `task_queue` break multi process resume and cleanup, `apps/agent/app/application/use_cases/run_autonomous_loop.py:248`
**Problem**: Paused sandboxes are stored in a process local Python dict `SandboxRegistry` (`apps/agent/app/infrastructure/sandbox/registry.py:6-27`). In a separate ARQ worker process or after API/worker separation: `abort_task` (`apps/agent/app/api/v1/endpoints/tasks.py:473`) and `handle_interruption_timeout` (`apps/agent/app/infrastructure/queue/worker.py:98-99`) fail to terminate the paused sandbox; `resume()` (`apps/agent/app/application/use_cases/run_autonomous_loop.py:252-260`) creates a brand new unrecorded sandbox (never updating `sandbox_runs`, which enforces uniqueness on `task_run_id`) while leaving the original sandbox running; and `resume_task_job` (`apps/agent/app/infrastructure/queue/worker.py:202-220`) omits `task_queue=get_task_queue()` when instantiating `RunAutonomousLoopUseCase`.
**Why it matters**: Releasing the ARQ worker on pause (Spec 0006 AC-4) only works reliably if another worker process can reconnect to or terminate the paused microVM by `sandbox_id` and schedule watchdogs on subsequent interrupts; otherwise sandboxes leak and nested interrupts never expire.
**Suggested fix**: Support provider level reconnection and remote termination by `sandbox_id` (for E2B microVMs) rather than relying solely on an in memory dict, record sandbox replacement or termination in `sandbox_run_repo`, update `task_runs.status = "cancelled"` and `sandbox_runs.terminated_at` in `abort_task`, and pass `task_queue=get_task_queue()` inside `resume_task_job`.

### 🟠 Permanent Redis disable latch and swallowed ARQ enqueue errors strand tasks, `apps/agent/app/infrastructure/queue/arq_queue.py:55`
**Problem**: Both `ArqTaskQueue._get_pool` (`apps/agent/app/infrastructure/queue/arq_queue.py:36-57`) and `InMemoryOrRedisEventStreamer._get_client` (`apps/agent/app/infrastructure/events/redis_streamer.py:31-56`) permanently latch `self._redis_disabled = True` after any single connection error and bind one client/pool to a module level singleton across asyncio event loops. Worse, `ArqTaskQueue.enqueue_resume_task` (`apps/agent/app/infrastructure/queue/arq_queue.py:76-95`) and `schedule_interruption_watchdog` (`apps/agent/app/infrastructure/queue/arq_queue.py:107-127`) catch and swallow `enqueue_job` exceptions, returning a synthetic `job_id` as if queued.
**Why it matters**: If Redis experiences a brief startup delay or transient failure, `respond_to_interruption` commits `status="in_progress"` and returns `200 accepted` while never queuing `resume_task_job`, leaving the task stuck indefinitely, and Redis remains disabled for the life of the process.
**Suggested fix**: Remove the permanent `_redis_disabled` latch (use bounded retry/cooldown or explicit test injection for in memory mode), recreate closed or mismatched event loop clients safely, and surface enqueue failures (returning `503` from `/respond` or rolling back/retrying) instead of silently swallowing them.

### 🟠 Terminal transcript hydration and live SSE race duplicates or drops logs and overwrites state, `apps/web/src/app/(console)/tasks/[id]/task-detail-client.tsx:185`
**Problem**: `TaskDetailClient` mounts `useTaskStream` (`autoConnect = true`) and simultaneously runs `loadTask` (`apps/web/src/app/(console)/tasks/[id]/task-detail-client.tsx:140-239`). For a terminal task, `loadTask` fetches `/transcript` while `useTaskStream` replays from cursor `0-0`; whichever arrives second either duplicates all log lines (when SSE appends on top of hydrated transcript) or is ignored (when `hydrateSnapshot` sees `prev.length > 0` without `replaceLogs: true` at `apps/web/src/lib/use-task-stream.ts:141`). For an active task, a late `loadTask` response passes `status: data.status` and `interruption: null` (`apps/web/src/app/(console)/tasks/[id]/task-detail-client.tsx:224-228`), overwriting live `task.interrupted` or `task.status` events received via SSE.
**Why it matters**: Developers inspecting completed runs see duplicated logs or truncated streams, and developers watching an active task that pauses for clarification while `loadTask` is in flight lose the clarification banner.
**Suggested fix**: Sequence initial task metadata/transcript loading before opening the live SSE stream (or skip SSE entirely when `data.status` is already terminal, and pass the last seen `event_id` from `/transcript` as the starting cursor for SSE), and avoid overwriting newer SSE driven state with stale initial snapshot fields.

### 🟠 `ClerkTaskDetail` ignores `isLoaded` and shadows `orgId`, causing silent 401 load failures, `apps/web/src/app/(console)/tasks/[id]/clerk-task-detail.tsx:16`
**Problem**: `ClerkTaskDetail` (`apps/web/src/app/(console)/tasks/[id]/clerk-task-detail.tsx:16-28`) does not check `isLoaded` from `useAuth()` and computes `resolvedOrgId = initialOrgId || orgId || undefined` (shadowing live `orgId` changes behind the server prop). When `getToken()` returns `null` before client session hydration finishes, `TaskDetailClient.loadTask` (`apps/web/src/app/(console)/tasks/[id]/task-detail-client.tsx:142-163`) sends an unauthenticated request, silently returns on `401`, and leaves hardcoded mock metadata displayed, while `useTaskStream` (`apps/web/src/lib/use-task-stream.ts:181-185, 376`) locks `pendingInitialToken = null` for the initial fetch and burns its single `401` retry.
**Why it matters**: On initial page loads before Clerk client hydration completes, or after client organization state updates, task metadata silently fails to load and live streaming suffers an unnecessary `401` round trip or fails completely.
**Suggested fix**: Wait for `isLoaded` (or skip sending unauthenticated fetches when `getToken` returns `null`), derive `resolvedOrgId` from live `orgId ?? initialOrgId`, and only treat `pendingInitialToken` as populated when a non null token was resolved.

### 🟠 `useTaskStream` does not reset state or `Last-Event-ID` when `taskId` changes, `apps/web/src/lib/use-task-stream.ts:101`
**Problem**: `useTaskStream` initializes `logs`, `steps`, `interruption`, `status`, `error`, and `lastEventIdRef` on first mount (`apps/web/src/lib/use-task-stream.ts:101-110`) and restarts the stream when `taskId` changes (`apps/web/src/lib/use-task-stream.ts:384`), but never resets those states or `lastEventIdRef.current`.

**Suggested fix**: Reset `lastEventIdRef.current = null` and reset hook state (`logs`, `steps`, `interruption`, `status`, `error`) inside a `useEffect` keyed on `taskId` (or reset in the stream setup effect whenever `taskId` changes).

## Minor
### 🟡 Terminal SSE replay truncates at 500 events and live stream lacks disconnect/crash exit checks, `apps/agent/app/api/v1/endpoints/tasks.py:257`
**Problem**: In `stream_task_events`, the terminal branch (`apps/agent/app/api/v1/endpoints/tasks.py:257-279`) reads only `count=500` events without looping (truncating streams up to the 10,000 cap) and always emits a duplicate `task.status` frame lacking `event_id` and `timestamp`. The live loop (`apps/agent/app/api/v1/endpoints/tasks.py:281-305`) also never checks `await request.is_disconnected()` or periodic DB status if a worker dies without appending `task.status`.
**Why it matters**: Long terminal runs lose events past 500 on reconnect, and live SSE clients hang forever waiting on pings if a worker crashes before emitting `task.status`.
**Suggested fix**: Loop `read_events` until exhausted in the terminal branch, omit the synthetic `task.status` if the stream already ended with one, check `await request.is_disconnected()` in the live loop, and periodically recheck DB task status when idle.

### 🟡 Events emitted to Redis before PostgreSQL commit, `apps/agent/app/api/v1/endpoints/tasks.py:413`

**Why it matters**: SSE clients reacting immediately to `task.resumed` or `task.status` can query `GET /tasks/{id}` before the transaction commits, or observe events for a transaction that rolls back.
**Suggested fix**: Append Redis Stream events only after `await db.commit()` succeeds.
