## Summary
This change implements the foundational PostgreSQL schema, SQLAlchemy models, clean architecture repository adapters, and Drizzle ORM read schemas for tenant isolation, task execution, and credential security under Spec 0002. While the architecture cleanly separates domain entities from infrastructure and implements strong authenticated encryption with database immutability triggers, the checkpoint optimistic concurrency mechanism contains a concurrency race condition that allows concurrent workers to silently overwrite execution state. In addition, task state machine transitions are unvalidated in the repository layer, sandbox allocation leaks raw database exceptions on collision, and hardcoded development encryption keys remain active when debug mode is disabled.

## Blockers

### 🔴 Broken optimistic concurrency control in checkpoint updates, `apps/agent/app/infrastructure/db/repositories/task_run_repository.py:90`
**Problem**: The `update_checkpoint` method reads `TaskRunModel` with a standard `select` query, tests `model.version != expected_version` in Python application memory, and then increments `model.version` in memory before flushing. Under PostgreSQL default transaction isolation (READ COMMITTED), two concurrent workers updating the same run will both read the same initial version, pass the Python version equality check, and execute an `UPDATE` statement setting the identical incremented version number. Because SQLAlchemy ORM mapper versioning (`version_id_col`) is not configured on `TaskRunModel`, the generated SQL `UPDATE` statement contains no `WHERE version = :expected_version` condition. The second committing transaction silently overwrites the first worker checkpoint state without raising `ConcurrencyError`.
**Why it matters**: In production, concurrent agent iterations or retries will silently overwrite and lose LangGraph checkpoint graph state, corrupting task execution history and leading to split brain execution states.
**Suggested fix**: Either configure native SQLAlchemy versioning by adding `__mapper_args__ = {"version_id_col": version}` to `TaskRunModel` so that SQLAlchemy appends the version check to the generated `UPDATE` statement and raises `StaleDataError`, or rewrite `update_checkpoint` to execute an atomic SQL `UPDATE` statement with `WHERE id = :task_run_id AND org_id = :org_id AND version = :expected_version` and raise `ConcurrencyError` if `rowcount == 0`.

## Major

### 🟠 Unvalidated task state machine transitions, `apps/agent/app/infrastructure/db/repositories/task_repository.py:112`
**Problem**: Spec 0002 explicitly specifies a defined task state machine (`queued` to `in_progress` to `awaiting_approval` to `in_progress` to `completed`, `failed`, or `cancelled`) and lists `InvalidStateTransitionError` as an expected error for `TaskRepository.update_status`. However, `SqlAlchemyTaskRepository.update_status` directly assigns `model.status = status` without validating whether the requested transition is valid from the current status. A task can transition from `completed` backwards to `queued`, from `failed` to `awaiting_approval`, or to arbitrary invalid status strings. Furthermore, domain entities do not encapsulate transition rules, leaving `InvalidStateTransitionError` completely unused.
**Why it matters**: Corrupts task lifecycles in production by permitting impossible status jumps, breaking worker orchestration loops, billing calculations, and console user interface status assumptions.
**Suggested fix**: Define permitted state transitions on the `Task` domain entity or a dedicated state machine validator, and call this validation before updating status in `SqlAlchemyTaskRepository.update_status`, raising `InvalidStateTransitionError` when an illegal transition is attempted.

### 🟠 Missing conflict handling in sandbox allocation leaks database driver exceptions, `apps/agent/app/infrastructure/db/repositories/sandbox_run_repository.py:41`
**Problem**: Spec 0002 defines a strict one to one relationship between task runs and sandbox runs (`AC-4`, unique constraint on `task_run_id`), and specifies `ConflictError` as the required domain exception when an allocation already exists for a run. However, `SqlAlchemySandboxRunRepository.record_allocation` does not check for an existing sandbox record before inserting, nor does it catch database constraint violations on flush. Attempting to allocate a second sandbox for the same task run causes an unhandled `sqlalchemy.exc.IntegrityError` to escape the repository.
**Why it matters**: Violates Clean Architecture by leaking internal database driver exceptions across repository boundaries, causing unexpected 500 server crashes instead of clean domain error handling in workers and API services.
**Suggested fix**: Query for an existing `SandboxRunModel` for `task_run_id` before inserting or catch `IntegrityError` on `session.flush()` and raise `ConflictError` when a sandbox is already assigned to the given task run.

### 🟠 Hardcoded development encryption key used as fallback in production mode, `apps/agent/app/core/config.py:21`
**Problem**: `Settings` sets a static hardcoded base64 encryption key as the default value for `CREDENTIALS_ENCRYPTION_KEY` while defaulting `DEBUG` to `False`. If the application is deployed to staging or production without explicitly setting the `CREDENTIALS_ENCRYPTION_KEY` environment variable, the service boots successfully and encrypts sensitive customer repository tokens using a publicly known key committed to Git.
**Why it matters**: Complete compromise of encrypted credentials at rest if deployed without an explicit environment variable override.
**Suggested fix**: Add a Pydantic model validator on `Settings` ensuring that when `DEBUG` is false, `CREDENTIALS_ENCRYPTION_KEY` must be explicitly provided in the environment and cannot match the known development fallback key.

## Minor

### 🟡 Duplicate configuration field declarations, `apps/agent/app/core/config.py:19`
**Problem**: `DATABASE_URL` and `CREDENTIALS_ENCRYPTION_KEY` are declared twice consecutively in `Settings` (lines 19 to 21 and lines 22 to 26). While Python class body execution overrides the earlier declarations with the later ones, duplicate fields create confusion and risk configuration drift when modifying settings.
**Why it matters**: Clutters core configuration and creates potential maintenance bugs if defaults differ between declarations.
**Suggested fix**: Remove lines 19 to 21 so each configuration setting is declared exactly once.

### 🟡 Drizzle ORM schema misses secondary indexes present in Alembic migrations, `apps/web/src/db/schema.ts:40`
**Problem**: The PostgreSQL schema generated by Alembic defines `ix_repositories_github_repo_id` on `repositories(github_repo_id)` and standalone foreign key indexes across execution tables. In `apps/web/src/db/schema.ts`, the index on `githubRepoId` is omitted from the `repositories` table definition, and composite indexes on `tasks` omit the descending sort order defined in PostgreSQL.
**Why it matters**: Web console queries filtering repositories by GitHub repository identifier will not match database metadata, and automated schema introspection checks (`drizzle-kit introspect`) will flag false positive schema drift.
**Suggested fix**: Add `index("ix_repositories_github_repo_id").on(table.githubRepoId)` and matching foreign key indexes to `apps/web/src/db/schema.ts`.

### 🟡 Sandbox termination hardcodes terminated status and ignores timeouts or errors, `apps/agent/app/infrastructure/db/repositories/sandbox_run_repository.py:89`
**Problem**: Spec 0002 defines five sandbox lifecycle statuses (`allocating`, `active`, `terminated`, `timed_out`, and `error`). However, `record_termination` hardcodes `model.status = "terminated"` and accepts no status argument. There are no other methods on `SandboxRunRepository` to record a timeout or runtime allocation failure.
**Why it matters**: Sandboxes that hit hard memory or time ceilings or fail during container boot cannot be recorded as `timed_out` or `error`, causing all ended sandboxes to appear as cleanly terminated.
**Suggested fix**: Add an optional `status: str = "terminated"` parameter to `record_termination` in both the port protocol and SQLAlchemy adapter, validating against allowed terminal statuses.

### 🟡 Credential key version incremented on secret updates rather than master key rotation, `apps/agent/app/infrastructure/db/repositories/credential_repository.py:63`
**Problem**: In `SqlAlchemyCredentialRepository.store_secret`, line 63 increments `existing.key_version += 1` whenever an existing secret is updated with a new plaintext value. According to Spec 0002 (line 75 and line 281), `key_version` tracks the version of the master encryption key (`CREDENTIALS_ENCRYPTION_KEY`) used to encrypt the record, enabling future background key rotation jobs to identify which master key was used. Incrementing it on every user secret edit treats it as a secret revision counter.
**Why it matters**: When master key rotation is introduced, credentials that were edited multiple times will have artificial key version numbers (such as version 5) for which no corresponding master key exists.
**Suggested fix**: Keep `key_version` aligned with the active master encryption key version, or introduce a separate `revision` column if tracking user edit counts is desired.

* ⚪ `apps/agent/tests/test_data_model_integration.py:255`, `test_optimistic_concurrency_conflict` executes sequential calls with a stale version rather than launching concurrent asynchronous workers via `asyncio.gather` with separate database sessions, leaving real parallel race conditions unexercised.

## Strengths

* Strict Clean Architecture discipline with complete isolation between domain, application, and infrastructure layers; domain entities and repository ports have zero external framework dependencies.
* Robust cryptographic implementation using AES 256 GCM authenticated encryption with 96 bit random nonces, 128 bit authentication tag verification, and tampering protection.
* Clean PostgreSQL database guarantees including UUIDv7 primary keys, partial unique indexes supporting clean soft deletion re linking, and database triggers enforcing append only immutability on audit logs.
* Complete parity with frontend Drizzle ORM schemas in the Next.js web workspace providing TypeScript type safety across the monorepo.

## Test coverage

Test signal is `configured`. Overall test quality is high across unit and integration levels with 26 passing pytest tests in `apps/agent` and 12 passing vitest tests in `apps/web`. The test suite thoroughly covers cryptographic round trips, authentication tag tampering detection, tenant boundary isolation across repositories, soft deletion re linking, Alembic migration cycles (upgrade to head, downgrade to base, upgrade to head), and audit log database trigger immutability.

However, there is a notable testing gap around actual concurrency. The optimistic concurrency test (`test_optimistic_concurrency_conflict`) only exercises sequential calls with a stale version counter rather than testing concurrent coroutines running in parallel against separate database sessions. This gap allowed the race condition in `update_checkpoint` to pass tests unnoticed. Additionally, invalid state machine transitions and conflicting sandbox allocations have zero test coverage because neither is currently guarded in the repository implementations.
