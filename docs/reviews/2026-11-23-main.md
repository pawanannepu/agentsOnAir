## Summary
This change implements Slice 1 for the core autonomous engineer and reviewer loop under Spec 0004. It introduces database schema and migrations for review iterations and pull request tracking, GitHub webhook ingestion with HMAC signature verification, a sandbox workspace coordinator with baseline test execution, simulated Forge coder and Reviewer critic agents, and a cyclical execution loop use case. While the database schema, partial unique indexing, and multi scenario test harness provide a solid foundation, critical blockers prevent safe production deployment. Specifically, newly created files are excluded from sandbox git diff extraction causing empty reviews, the Docker sandbox provider executes commands directly on the host machine while leaking host environment secrets, and unsanitized branch parameters interpolated into shell execution strings allow remote command injection. In addition, task API endpoints lack authentication, unhandled exceptions leave tasks in progress permanently, and brittle error substring matching triggers false positive review failures.

## Blockers

### 🔴 Newly created untracked files excluded from sandbox git diff extraction, `apps/agent/app/infrastructure/sandbox/mock_sandbox.py:110` and `apps/agent/app/infrastructure/sandbox/docker_sandbox.py:111`
**Problem**: In `MockSandboxSession.get_diff` and `DockerSandboxSession.get_diff`, the diff extraction method executes `git diff HEAD`, and if empty, falls back to `git diff`. In Git, newly authored files created in the workspace via `write_file` are untracked. Untracked files do not appear in `git diff HEAD` (which also fails when HEAD has no initial commits) nor in `git diff`. As a result, when the agent authors a new file, `get_diff()` returns an empty string.
**Why it matters**: The Reviewer critic receives an empty diff for new files, `review_iterations.diff_snapshot` persists empty diff records, and host branch push extracts empty code changes, completely defeating autonomous verification.
**Suggested fix**: Stage untracked files before running diff extraction by executing `git add -A` followed by `git diff --cached`, or run `git add -N .` to mark untracked files as intent to add so that standard `git diff` includes new files.

### 🔴 Docker sandbox provider executes commands directly on host without container isolation and leaks host secrets, `apps/agent/app/infrastructure/sandbox/docker_sandbox.py:48`
**Problem**: `DockerSandboxProvider` is configured as the default sandbox provider in settings, but `DockerSandboxSession` does not run containers. Instead, it creates a temporary directory on the host filesystem and runs `asyncio.create_subprocess_shell` directly on the host machine. Furthermore, it initializes `full_env` using `os.environ.copy()`, passing the host process environment containing `DATABASE_URL`, `CREDENTIALS_ENCRYPTION_KEY`, and `GITHUB_WEBHOOK_SECRET` directly to sandbox commands.
**Why it matters**: Untrusted code executed during repository test runs has full access to the host operating system, local network, and production database credentials, directly violating the core security invariant of Spec 0004 requiring microVM or container isolation with zero access to host credentials.
**Suggested fix**: Implement real container isolation using Docker CLI or Docker SDK (`docker run` with resource caps and dropped privileges), isolate workspace volumes, and strip all internal host secrets from the container execution environment.

### 🔴 Unsanitized branch strings interpolated into shell execution permit command injection, `apps/agent/app/application/services/sandbox_workspace.py:45`
**Problem**: In `SandboxWorkspace.init_workspace`, shell commands are constructed via string interpolation: `f"git clone --branch {base_branch} --depth 50 {repo_url_with_read_token} ."` and `f"git checkout -b {work_branch}"`. The `base_branch` string is accepted directly from untrusted user payloads in `POST /api/v1/tasks` without validation, and `work_branch` contains values derived from trigger metadata. Because `execute_command` uses `create_subprocess_shell`, metacharacters like semicolons or backticks in branch names execute arbitrary shell commands.
**Why it matters**: Attackers can achieve remote code execution on the server by supplying malicious branch names in task creation requests or webhook metadata.
**Suggested fix**: Validate `base_branch` against a strict alphanumeric regex, sanitize branch names with `shlex.quote`, or switch `execute_command` to use argument lists with `asyncio.create_subprocess_exec` instead of raw shell evaluation.

## Major

### 🟠 Missing authentication and organization authorization on tasks endpoints, `apps/agent/app/api/v1/endpoints/tasks.py:70`
**Problem**: `POST /api/v1/tasks` and `GET /api/v1/tasks/{task_id}` accept `org_id` directly in request payloads or query parameters without verifying a Clerk Bearer JWT. Spec 0004 specifies Clerk JWT authentication, 401 unauthorized errors, and 403 forbidden responses on organization mismatch.
**Why it matters**: Any unauthenticated client can trigger autonomous engineering runs for arbitrary repositories or inspect private task runs, commit hashes, pull request coordinates, and review findings across organizations.
**Suggested fix**: Add a FastAPI authentication dependency that verifies incoming Clerk JWT bearer tokens, extracts the authenticated organization context, and verifies that the caller has membership in the requested organization.

### 🟠 Unhandled exceptions in loop execution leave tasks in progress permanently and block future runs, `apps/agent/app/application/use_cases/run_autonomous_loop.py:78`
**Problem**: `RunAutonomousLoopUseCase.execute` only catches `BaselineTestFailedError`. If an unexpected exception occurs during sandbox operations, agent reasoning, model gateway calls, or GitHub push operations, the exception bubbles up unhandled. While the `finally` block terminates the sandbox, `task_runs` remains in `pending` status, and `tasks` remains in `in_progress` status.
**Why it matters**: Because of the partial unique index `uq_tasks_active_repo_issue` on active tasks, a task stuck in `in_progress` permanently blocks all future webhook triggers and runs for that issue in the repository.
**Suggested fix**: Wrap the execution body in a general `try / except Exception` block that catches unexpected failures, transitions `task_runs` and `tasks` to `failed` with descriptive failure reasons, records an audit log event, and rolls back transactions cleanly before re-raising.

### 🟠 Substring match on error causes false positive review rejections on passing tests, `apps/agent/app/infrastructure/llm/agents.py:104`
**Problem**: In `ReviewerCriticAgent.evaluate`, test failure is evaluated via `"FAIL" in test_output or "error" in test_output.lower()`. If test output contains the word error in benign contexts (such as a test filename like `test_error_handling.py`, log messages, or docstrings while passing with exit code 0), the critic classifies it as a major blocking failure.
**Why it matters**: Autonomous runs fail review or waste outer repair cycles on successful test suites whenever test names or logs include the word error.
**Suggested fix**: Pass the structured test execution exit code from `ForgeResult` into `ReviewerCriticAgent.evaluate`, and only treat tests as failing when `exit_code != 0` or structured failure counts are positive.

### 🟠 Clean architecture layer violation where application use case imports directly from infrastructure, `apps/agent/app/application/use_cases/ingest_github_webhook.py:10`
**Problem**: `ingest_github_webhook.py` in the application layer imports `verify_github_signature` directly from `app.infrastructure.github.webhook`. According to `AGENTS.md` clean architecture rules, outer layers depend on inner layers, and application use cases must never import from infrastructure.
**Why it matters**: Breaks architectural boundaries and couples application domain use cases to concrete infrastructure implementation modules, impeding testability and portability.
**Suggested fix**: Move generic cryptographic webhook signature verification to `app.core.security` or define a signature verifier port in `app.application.ports` and inject the adapter.

## Minor

### 🟡 Repository clone url with read token hardcoded to None, `apps/agent/app/application/use_cases/run_autonomous_loop.py:84`
**Problem**: `workspace.init_workspace` receives `repo_url_with_read_token=None` hardcoded. The use case never calls `_github_gateway.get_installation_token(..., write_access=False)` to obtain a read token or construct the clone URL. In real sandbox microVMs or containers, the workspace is left empty rather than cloning repository files.
**Why it matters**: In real environments, Forge will operate on an empty workspace rather than the repository codebase.
**Suggested fix**: Request a read access installation token via `GitHubGateway` and pass the authenticated repository clone URL into `workspace.init_workspace`.

### 🟡 Unbounded in memory event history list leaks memory over time, `apps/agent/app/infrastructure/events/redis_streamer.py:16`
**Problem**: `InMemoryOrRedisEventStreamer` appends every streamed event to `self._events` without size limits or eviction. In addition, it does not actually publish to Redis despite accepting `redis_url`.
**Why it matters**: In a long running production process, storing every telemetry event in an unbounded Python list causes memory consumption to grow indefinitely.
**Suggested fix**: Cap `self._events` using a bounded collection (such as `collections.deque(maxlen=1000)`), or implement real Redis pub sub publishing and remove the unbounded in memory list in production mode.

### 🟡 Concurrent duplicate webhook deliveries can raise unhandled integrity error, `apps/agent/app/application/use_cases/ingest_github_webhook.py:151`
**Problem**: If duplicate webhook deliveries arrive simultaneously for the same issue, both pass the `find_active_by_repo_and_issue` check. The second concurrent `create_task` call triggers a database unique constraint violation on `uq_tasks_active_repo_issue`. Because `IntegrityError` is not caught, it causes a 500 server error instead of a 200 OK ignored response.
**Why it matters**: A 500 response causes GitHub to retry webhook delivery repeatedly, creating retry storms.
**Suggested fix**: Catch database `IntegrityError` in `create_task` or the use case and return `WebhookIngestResult(status="ignored", reason="active_task_already_exists")`.

### 🟡 Repository lookup by github id lacks installation scoping across organizations, `apps/agent/app/infrastructure/db/repositories/repository_repository.py:101`
**Problem**: `find_by_github_repo_id` queries `repositories` using only `github_repo_id`. In `RepositoryModel`, `github_repo_id` is only unique within an organization (`uq_repositories_active` on `org_id, github_repo_id`). If multiple organizations track the same repository, `scalar_one_or_none()` raises `MultipleResultsFound`.
**Why it matters**: Webhook processing crashes with a 500 error if two organizations link the same repository.
**Suggested fix**: Scope the repository lookup using both `github_repo_id` and the webhook payload installation identifier `github_installation_id`.

### 🟡 Missing overall execution timeout on multi cycle autonomous loop, `apps/agent/app/application/use_cases/run_autonomous_loop.py:121`
**Problem**: Spec 0004 specifies a hard timeout of 10 minutes total runtime (`SANDBOX_TIMEOUT_SECONDS = 600`). `RunAutonomousLoopUseCase.execute` does not wrap the multi cycle while loop in an overall timeout.
**Why it matters**: If an LLM call or network request hangs without timing out, the loop will run indefinitely and tie up worker resources.
**Suggested fix**: Wrap the execution loop in `asyncio.timeout(settings.SANDBOX_TIMEOUT_SECONDS)` and handle timeout by marking the task run as failed with `execution_timeout`.

## Strengths
* Clean relational schema, migrations, and Drizzle definitions that align across Python and TypeScript, featuring a partial unique index that prevents duplicate active runs per issue.
* Comprehensive integration test suite covering five critical loop lifecycle scenarios including happy path, cycle 2 repair, baseline failure abort, cycle exhaustion, and command timeouts.
* Pure Python domain entities and exceptions using dataclasses with `slots=True`, completely free of framework imports.

## Test coverage
Test signal is configured. The test suite exercises happy path webhook delivery, duplicate issue filtering, baseline test failure aborts, multi cycle repair iterations, and review cycle limits. However, several critical paths remain untested: `DockerSandboxSession` execution is not tested, error recovery when loop steps fail is uncovered, untracked file handling in diff extraction is untested, and the newly added TypeScript Drizzle table `reviewIterations` has no schema assertions in `apps/web`.
